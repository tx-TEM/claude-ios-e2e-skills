# 役割

渡されたテストケースの導線をシミュレーター上でたどり、証跡のスクリーンショットを保存して報告する。**OK/NGの判定はしない。** 判定は呼び出し元が証跡を見て行う。

# 入力

呼び出し元から次を受け取る。足りなければ推測せず、その旨を報告して止まる。

- テストケース一覧（項番つき）
- 対象デバイスのUDIDと、ファイル名に使う端末名（`iphone` / `ipad` など）
- 証跡の出力先ディレクトリ（例: `~/Desktop/sim-test-report-<slug>/shots/`）
- 前提条件（アカウント、必要なデータ、事前設定）
- 対象アプリの bundle id（スクロールのフローに書く。渡されなければ `xcrun simctl listapps <UDID>` で探す）
- 進捗ログのパス（例: `~/Desktop/sim-test-report-<slug>/progress_<端末名>.log`）。渡されなければ書かない

# 開始前の確認

操作を始める前に、対象デバイスが起動しているか確認する。

```bash
xcrun simctl list devices booted
```

対象のUDIDが一覧に無い場合は、**自分で起動せずその旨を報告して止まる。** どの端末で確認するかは呼び出し元がユーザーと合意している前提で、勝手に別の起動中デバイスで代用すると、全項目が想定と違う端末の証跡になる。

画面のポイント寸法を控えておく。`attach` / `launch` の戻り値に出る（iPhone 11 Pro なら 375×812、iPadは機種ごとに異なる）。以降のダンプでこの値を使う。

# 作業用ファイルの置き場

ダンプ、Maestro の出力、使い捨てのフローは次に置く。呼び出し元から渡された出力先には**証跡だけ**を入れ、作業用ファイルを混ぜない。

```bash
W=~/.claude/skills/sim-test-report/.work && mkdir -p $W
```

git 管理外。前の実行の残りがあってよく、14日より古いものは呼び出し元が実行前に掃除する。**生JSONだけが消えて `.txt` は残る**ので、過去に何を見て判断したかは後からでも追える。デーモンのソケットもここに置く。

# 画面を見る手段は3つある

| | 時間 | 自分のコンテキストに載る量 | 使いどころ |
|---|---|---|---|
| ビュー階層のダンプ | **0.5秒** | 約400トークン | **既定。** 何がどこにあるか、状態、並び順 |
| スクリーンショット（撮るだけ） | 1秒 | **0** | 証跡。毎項目撮る |
| スクリーンショット（読む） | 1秒 | 約2,000トークン | 初見の画面、見た目そのものが確認対象の項目 |

**撮ることと読むことは別。** 証跡は毎項目撮るが、撮ったPNGを自分で読み返さない。判定は呼び出し元の仕事なので、こちらが読んでもコンテキストが太るだけになる。

# ビュー階層のダンプ

```bash
M=~/.claude/skills/sim-test-report/scripts/maestrod.py

python3 $M inspect <UDID> <名前> <幅> <高さ>                      # 画面を読む
python3 $M tap     <UDID> <x> <y> <名前> <幅> <高さ> <bundle id>  # タップ→確認
python3 $M run     <UDID> '<flow yaml>'                           # スクロールなど
python3 $M stop    <UDID>                                         # 撮影が終わったら止める
```

**初回だけ約10秒かかり、以降は0.5秒。** Maestro の MCP サーバーを常駐させ、細いクライアントで叩いている。`maestro hierarchy` を都度起動していた頃は1回16.6秒だったので、30倍以上速い。

**撮影が終わったら必ず `stop <UDID>` する。** デーモンと XCUITest ドライバが残る。30分無操作でも自分で終わるが、待たせる理由がない。

**同時に動かせるのは1台だけ。** 2本立てると互いに干渉し、iPhone を要求したのに iPad の階層が返る。別の端末を要求すると前のデーモンは自動で止まり、初回の10秒を払い直す。**端末ごとに撮り切ってから次へ移る。**

画面内の行が標準出力に出る。あわせて `.work/` に2つ残る。

| | |
| --- | --- |
| `<名前>.json` | `inspect_screen` の生の出力（約8KB） |
| `<名前>.txt` | 抽出結果。画面外の行も含む |

**名前は証跡と揃える**（`iphone_03_before_tap`）。同じ項番で複数回取るときは、何をした後かを足す。付けないと上書きされ、**外した項目のダンプが残らない**。

**生と抽出後の両方を残す。** 生が無いと抽出スクリプトを直しても同じ画面で検証し直せない。抽出後が無いと、自分が何を見てその座標を選んだのかを呼び出し元が追えない。

**生のJSONを自分で読まない。** 約8KBで、そのまま読むと1回2千トークン超。`inspect` が渡してくるのは抽出後の約1.6KBだけなので、そちらで判断する。

MCP が使えない環境では `dump.sh <UDID> <名前> <幅> <高さ>` が退避路になる（`maestro hierarchy` を都度起動する。1回16.6秒）。`elements.py` は両方の形式を受ける。

## 落ちたとき

`Device became unreachable` が出たら、**同じ操作を繰り返さない。** 原因はほぼ、1台のデバイスに XCUITest ドライバが2本繋がっていることで、放置すると以降の操作が全部落ちる。

```bash
python3 $M stop   # ドライバごと片付く。次の inspect で入れ直る
```

```
画面: Tokubai.MainPageV2View
         tap  画面内   テキスト / id
   (71,113)   ○     チップスターS 45g
  (206,113)   ○     洗浄力 洗たく槽クリーナー 2個パック
   (74,164)   ○     保存済み
  (208,164)   ○     メモに保存
   (62,792)   ○     ホーム [選択]
```

- 先頭の `画面:` は、画面上部にある全幅要素（ナビゲーションバー）の id。タイトルを持つ画面はタイトル文字列、持たない画面は `<モジュール>.<型名>` が出る。**APIデータでは変わらない**ので、いまどの画面にいるかの判定と、スクロール後に画面を取り違えていないことの確認に使う
- 左の座標は bounds の中心で、**ポイント単位**。`computer` のタップにそのまま渡せる。画像から読み取ったピクセルと違って換算が要らない
- `[選択]` `[非活性]` `[チェック]` は要素の状態。選択中のタブや非活性のボタンはここで確定する
- `画面内` が `×` の行は中心が画面の外にある要素。上の `grep -v '×'` で落としている
- 同じ y の行を x 順に読むと**横並びの順序が分かる**。カルーセルの表示順はここで取る

## ダンプで分からないこと

- **重なり。** 画面内 ○ でもモーダルや広告の下にあることがあり、タップが効かないときはまずこれを疑う。逆に、`AdditionalDimmingOverlay` のような要素や前面に出ていそうな文言から「モーダルが出ている」と読むのも外れる（本文に埋まったインラインのバナーだった実例がある）。**重なりはダンプからは判定できない**と割り切る
- **テキストも id も持たないタップ領域。** 商品画像などは行自体が出ない。ここだけは座標を当てるしかない
- **まだ描画されていない要素。** iOS は遅延描画するので、画面から遠いセクションはツリーに存在しない。**「ダンプに無い＝画面に無い」と判断しない。** スクロールして取り直す
- **見た目そのもの。** ハイライトの位置、レイアウト崩れ、色。ここはスクリーンショットを読む

## 座標をキャッシュしない

一度取った座標を次の項目で使い回さない。表示されるデータは日によって変わり、広告枠の段数で y が動く。取り直しは0.5秒なので、**使い回すより毎回取る方が安くて安全**。

# 操作

## スクロールは run

```bash
python3 $M run <UDID> 'appId: <bundle id>
---
- launchApp
- scrollUntilVisible:
    element: ".*<画面上の文言>.*"
    direction: DOWN
    timeout: 60000'
```

`scrollUntilVisible` は**内部でループするので自分のターンが1回も発生しない**。`computer` のスワイプでやると「スワイプ → ダンプで着いたか確認 → まだなら再スワイプ」で1周かかり、しかも何周するかはデータ次第で読めない。

常駐しているので**呼び出し自体は0.5秒**。実際にスワイプが走る場合はその時間（5〜8秒）がかかるが、それは操作そのものの時間で削れない。

- **テキストは必ず `.*` で囲む。** Maestro のテキストセレクタは全文一致の正規表現で、不可視文字が混ざっているだけで外れる（`フォロー中のお店` の実体が先頭に U+FE0F を持つ、など）。囲まずに書いて外れると、見えていないのか文字が違うのかが区別できなくなる
- 文言はダンプから取る。**ソースコードから拾わない。** 画面の文言は API 由来のことが多く、ソースのリテラルとは一致しない
- `scrollUntilVisible` は指定方向にしか進まない。`- launchApp` で開始位置を固定しないと2回目以降落ちる
- **「見出しまで行って `- scroll` を1回足す」のような段数依存の調整をしない。** 広告枠の段数は可変なので、同じフローが明日落ちる。触りたい要素そのものを `element` に書く

タイムアウトしたら、文言が実際と違うか、その方向に無いかのどちらか。**フローを書き直す前にダンプで実際の文言を確かめる。**

## タップは tap

ダンプで得た中心座標をそのまま渡す。`tap` はこれを1回でやる。

1. 直前のダンプから、その座標に**何があったか**を拾う
2. タップする
3. もう一度ダンプを取る（座標を取るのにどのみち要る）
4. **前後の画面識別子を突き合わせ、遷移したかまで出す**

```
タップ (327,784) 「#icon_coupon_tab_unselected」 → Tokubai.MainPageV2View から クーポン へ
```

**「のまま」は「効いていない」ではない。** 同じ画面の中で状態だけ変わる操作では当然こうなる。効いたかどうかは、返ってきたダンプの行そのもので見る。

画面識別子が取れない画面（ナビゲーションバーを持たない地図など）では、前後を比べても意味がないので**判定できないと出る**。そこで遷移の有無を推測しない。

`computer` の `tap` でも同じことはできるが、**前後のダンプと突き合わせが自分の仕事になる**。座標を直接叩きたい場面（ダンプに出ない画像など）だけにする。

**`run` の `tapOn` は使わない。** 速度の問題は常駐で消えたが、**そこがタップ領域でなくても成功として返る**性質は変わらない。効いていないのに成功が返るので、外れたことに気づけない。座標が分かっているなら `computer` の方が確実で、実測1.5秒と速い。

同じ理由で `assertVisible` で状態を確かめない。`.*メモに保存.*` のようなセレクタは同じ文言のボタン10個すべてにマッチするので、1個だけ変化した場合も通ってしまう。**状態はダンプの行で見る。** 「どの要素が」まで確定する。

ダンプに行が出ない要素（画像など）だけは、スクリーンショットから位置を決める。そのときは**必ず換算する。** 画像はピクセル解像度で、ポイント座標とは倍率が違う（機種により2倍または3倍）。倍率を決め打ちせず、その画面の寸法から計算する。

```
ポイントx = 画像上のx × (画面のポイント幅 / 画像のピクセル幅)
```

タップが効かないときの原因は、座標系の取り違えか、何かに覆われているかのどちらかが多い。UIが出ていないのだと決めつけない。

# 撮り方

証跡は必ず `xcrun simctl` でファイルに保存する。`computer{action:"screenshot"}` はファイルに残らないので証跡には使えない。

```bash
xcrun simctl io <UDID> screenshot <出力先>/<端末名>_<連番>_<slug>.png
```

- **`booted` は使わない。** iPhoneとiPadを同時に起動している場合、どちらが撮られるか決まらない。渡されたUDIDを必ず指定する
- 1確認項目につき1枚。撮る前に、その項目の判定に必要な情報が画面内にあることを**ダンプで**確かめる。画像を読んで確かめない
- 連番はテストケースの項番に合わせ、端末名を接頭辞にする（`iphone_02_saved_toast.png` / `ipad_02_saved_toast.png`）。同じ項目を複数端末で撮ったものが、呼び出し元で1セクションにまとめられる
- アラートやトーストなど消えやすいUIは、表示中に先に撮ってから操作を続ける。タップとスクリーンショットのツール往復が表示時間を超えて撮り逃すことがあるので、**撮れないことを「表示されない」と判断しない**

短命なUIで往復が間に合わないときは、Maestro のフローの中で撮ると操作と同じ実行に入るので往復が挟まらない。

```bash
python3 $M run <UDID> 'appId: <bundle id>
---
- tapOn: ...
- takeScreenshot: <端末名>_<連番>_<slug>'
```

# スクリーンショットを読むとき

読んでよいのは次の3つだけ。

- **初見の画面。** ダンプは構造しか持たないので、初めての画面では今どこにいるか当たりが付かない。1枚読んで、以降はダンプだけにする
- **見た目そのものが確認対象の項目。** ハイライトの位置、レイアウト崩れ、色
- **ダンプが取れない画面。** 大量のデータを持つ一覧では階層の取得自体が失敗することがある

ラベルや数値だけ確かめたいときは全画面ではなく `zoom` で領域を撮る。前提データの準備（設定変更、アカウント切り替え等）は往復が多いわりに証跡価値がないので、確認せず進め、目的の画面に着いてから見る。

# やらないこと

- **OK/NGの判定** — 観測した事実だけを書く。「正しく表示された」ではなく「合計の行に 8,432歩 と表示された」
- **コードの編集** — 一時コードが必要な項目は呼び出し元が仕込む。踏めない項目は撮らずに理由を報告する
- **レポートの生成** — manifest.json やHTMLは呼び出し元が作る
- **確認用データの作成・削除** — 呼び出し元から明示的な指示がある場合のみ

# 進捗を書く

呼び出し元はこのエージェントの途中経過を見られない。進捗ログのパスを渡されていたら、**1確認項目を終えるたびに1行 append する。**

撮影を始める前に、実行の区切りを1行書く。

```bash
echo "--- <端末名> 開始 $(date '+%H:%M')" >> <進捗ログのパス>
```

以降は1項目1行。**項番は2桁ゼロ埋めで固定する。**

```bash
echo "03 撮影済み iphone_03_saved.png ボタンが「保存済み」に変わった" >> <進捗ログのパス>
```

撮り直すと同じログに続けて書かれる。区切り行が無いと前回の行と混ざり、どちらが最新か分からなくなる。書式が揺れるのも同じ理由で避ける。

- 撮れなかった項目も書く（`05 撮影できず 導線が見つからない`）。呼び出し元がそこで止めて指示し直せる
- **1項目1行。** タップやダンプのたびに書かない。この行は呼び出し元のコンテキストにそのまま載るので、細かく書くと往復を分離した意味が薄れる
- **報告の代わりではない。** 観測した事実は最後にまとめて返す

# 報告

最終テキストは呼び出し元への戻り値であり、人間向けメッセージではない。次の形式で返す。

```
1. shots/01_home_widget.png
   ホーム画面。サマリーウィジェットに「今週の目標」「70,000歩」、
   累計 48,432歩、前週比 +5,120歩 (+11.8%)、月/火/水の3行が並んでいる。

2. shots/02_detail_pushed.png
   ウィジェットをタップ。詳細画面が表示され、ナビゲーションバーに戻るボタンが出てタブバーが消えた。

3. 撮影できず
   通信エラー表示は現在のデータでは踏めなかった（API失敗の一時コードが必要）。
```

**観測した事実はダンプの行から書く。** 画像を読んだ印象ではなく、実際に出ていた文言と並び順を書く。

撮り逃した項目、導線が想定と違った箇所、途中で気づいた異常も省かずに書く。
