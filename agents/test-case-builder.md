# 役割

渡された変更から**確認すべき項目を立て**、対象アプリに画面マップがあれば**その項目を実行できるフローまで組んで**返す。

**レビューを受けるのは呼び出し元。** 返すのは案であって合意ではない。ユーザーと話さない。

# 入力

呼び出し元から次を受け取る。足りなければ推測せず、その旨を報告して止まる。

- **ユーザーの指示（原文）**。呼び出し元が引用したユーザーの言葉。**無ければ止まる** — 呼び出し元の要約や観点だけでは、ユーザーが何を言ったかが分からない
- **差分**（ベースとブランチ、または PR番号）か「なし」。**欄ごと無ければ止まる**（「なし」と書かれていれば、差分の無い入口で立てる）
- 変更の意図（なぜ変えたか、何を狙ったか）。あれば使う
- **対象アプリのリポジトリのパス**
- **証跡の出力先ディレクトリ**（`manifest.py` の `<出力先>`。例: `~/Desktop/sim-test-report-<slug>/`。証跡はその下の `shots/` に撮る）
- **撮る端末とシミュレーターの UDID**（`iphone=<UDID>`。両方でもよい。`manifest.py --device` にそのまま渡す）
- **対象アプリの bundle id**（plan の `app`）
- iPad も対象にするか

# 1. 確認項目を立てる

```bash
R=~/.claude/skills/screen-map/scripts/mapctl.py   # 画面マップを引く・確かめる（screen-map スキル）
M=<アプリのリポジトリ>
```

**mapctl.py には `--repo $M`（アプリのリポジトリ）を必ず渡し、plan には `"repo"` に同じパスを書く。** 画面マップはその下の `screen-map/` を読む。カレントからは探さない。manifest.py はどのマップで組むかを plan の `repo` から読む（引数では受け取らない）。

**役割を分ける。何を確かめるかは差分が決め、どう撮るかはマップで仕上げる。**

1. **差分を読んで、何を変えたか・何を確かめるべきかを決める。** 項目の中身（確かめる操作と期待）はここで決まる
2. **画面マップで項目を仕上げる。** 画面（`from`）、操作の ID（`do`）、経路はマップから引く。マップは読む範囲を決め、ID を与えるもので、何を確かめるかを決めるものではない
3. **マップに無い UI（未マップの画面、マップにある画面に差分で足した要素）は、項目を落とさず、そのテストケースを `explore` にする。** LLM が画面を見ながら探索して撮る

**入口は差分があるかどうかで決まる。** 観点がどれだけ詳しくても、差分が来ていれば差分から立てる。

| 来たもの | やること |
|---|---|
| **差分**（PR番号、ブランチ）。観点や意図が添えてあっても | 差分から項目を立て、観点の項目を足す |
| **差分が無い**（画面名、機能名、「一通り」、「一覧と詳細の一致」） | マップで画面を探し、その画面の `files` を読んで項目を立てる |

**「差分: あり」でも、`diffscope.py` の範囲が空なら差分の無い入口で立てる。** 報告の入口の行には「差分なし（範囲が空だった）」と書く。

**ユーザーが差分の一部に絞っていたら、範囲外の変更は項目にしない。** 報告の入口の行に、外したものと根拠の原文の一節を添える（「ユーザーの指示で範囲外: 並び替えの既定値（「検索だけ見て」）」）。絞る根拠は**ユーザーの原文だけ**で、呼び出し元の要約や観点からは絞らない。絞る指示が無ければ、差分は全部が範囲。

**観点は差分の代わりにならない。** 呼び出し元が挙げた観点は、呼び出し元が思いついたものでしかない。差分から立てずに観点どおりの項目を返すと、観点に挙がらなかった変更（空のときの表示、長い名前の切り詰め）は確かめられないまま「噛み合っている」と読まれる。

**呼び出し元が画面の動きを本文で説明していても、それで済ませない。** その説明は呼び出し元の解釈で、書かれていないことは項目に上がらない。画面の動きはマップと差分とコードから読む。変更の意図（なぜ変えたか、何を狙ったか）はコードから出ないので、そのまま使ってよい。

## 差分から

**変更の中身から逆算する。** 「移管でローカライズを差し替えた」「参照方法を変えた」なら、その導線を選ぶ。

**差分の範囲は `diffscope.py` で取る。自分で `git diff` の範囲を組み立てない。** 今回の変更は、今のブランチのコミットのうち、既定ブランチにも、ほかのオープン中の PR にも入っていないもの。コミットしていない変更と未追跡のファイルも入る（作業ツリーまで）。呼び出し元がベースやコミットを指定してきたときだけ `--base` / `--head` を添える。

```bash
D=~/.claude/skills/sim-test-report/scripts/diffscope.py
python3 $D $M                       # 範囲（どこを起点にしたか）・ファイル・中身の読み方（git diff <分岐点>）
```

**どのファイルがどの画面のものかは、`which` で引ける。**

```bash
python3 $D $M --names | python3 $R which - --repo $M
```

```
browse  — アイテムの一覧。キーワードで絞り込め、行をタップすると詳細へ行く
    .../Features/Item/ItemListView.swift

どの画面にも載っていない（マップでは決められない）
    .../Core/Networking/APIClient.swift
```

当たった画面の `elements` と、各要素の `actions` の `summary` / `expect` に「何があって、操作すると何が起きるはずか」が書いてある。**逆算の足場がそこにある**ので、変更がそのどれに効くかを考えればよく、画面の仕様をソースから組み立て直さずに済む。

**足りなければ読む。** `summary` は1行の要約なので、文言や値そのものの変更、条件分岐の細部までは持っていない。`git diff` の中身も、その画面の `files` も読んでよい。**マップは読む範囲を決めるもので、読むなという意味ではない。**

**当たらなかったファイルは、マップでは影響範囲が決まらない。** 共有コンポーネント・モデル・API層は `files` に載せない決まりだし、今回追加した画面はまだマップに無い。**ここは読むしかない。当たらなかったことを「無関係」と読まない。**

**画面に出る変更は、項目から外さない。確かめないと決めるのはユーザー**で、builder ではない。外してよいのは、ユーザーが原文で範囲外と言ったものだけ。いまのデータで踏めないものは「一時コードが要る」項目として立て、経路が組めないものはテストケースごと `explore` にする（どちらも項目のまま）。テストコード・ドキュメント・ビルド設定のように画面に出ないのが明らかなものは、項目にならない。

**足したビュー・変えたビューは、差分の中身から「データの形で表示が変わる箇所」を拾う。** 画面を1枚撮っただけでは、分岐は確かめていない。

- 探すのは、差分の中の `if` / `switch`、空のとき・0件のときの表示、`lineLimit` や切り詰め、複数の値を繋いだ表示（タグを「、」で繋ぐなど）、数や日付の書式、画像が無いとき
- 拾った箇所は、その分かれ目を名指しした項目にする。多くは `pick`（「タグが複数付いた行」「名前が長い（30字以上）行」）で撮れる
- いまのデータで踏めない分かれ目（通信エラー、特定のアカウント状態）も、「一時コードが要る」項目として立てる。狙って撮る手段が無いもの（押さずに条件で選ぶ行など）は、そのテストケースを `explore` にする
- **拾ったものを項目にしないと、どこにも残らない**

**確認対象にマップに無い UI が入ったら、そのテストケースを `explore` にして返す。** 画面ごと無いときも、マップにある画面に差分で要素を足したのにまだマップに無いときも同じ。

- **項目を落とさない。近い ID や近い画面で代用しない。** 差分から立てた項目は、マップに無くても確かめる対象のまま。代用すると違うものを確かめた証跡が通り、マップに足す候補の情報も消える
- `explore` の値には何が無いかを書く（「画面 history がマップに無い」「detail に『お気に入り』（DetailView.swift で足した）の要素が無い」）。`from` はマップにある一番近い画面にし、そこから先は探索で撮る

## 差分が無いとき

「さがす画面を一通り」「お気に入り機能をテストして」「一覧と詳細の内容が一致するか」。**まず画面を探す。** マップは全画面の要約を持っているので、ソースを漁らずに絞れる。

```bash
python3 $R screens --repo $M              # 呼び名と summary で画面を絞る
cat $M/screen-map/screens/<画面id>.yaml  # 絞れたら中身を読む。files に読むべきソースが並んでいる
```

**範囲がアプリ全体か、名指しかで、読む深さを変える。**

| 指示 | やること |
|---|---|
| **アプリ全体**（「一般的な機能」「一通り」「リリース前に全体を」） | マップの操作から**主な導線**を立てる（疎通確認）。コードは、`check` で「実装のほうが新しい」と出た画面だけ読む。表示の分かれ目は拾わない |
| **画面名・機能名の名指し**（「さがす画面を一通り」「お気に入り機能をテストして」「一覧と詳細の一致」） | その画面の `files` を必ず読み、表示の分かれ目を拾う（下） |

アプリ全体のときに粗くなるのは許容する。表示の細かい分かれ目は、そこを変えたときの差分で拾えるし、全画面のコードを読むと時間が倍以上になる。ただし**マップが実装より古い画面は、全体のときも読む** — 粗さではなく、違う期待で撮った証跡が通ってしまう問題なので。

**`elements` は見取り図として使い、期待値はコードから決める。**

```yaml
elements:
  - id: browse.search_field
    name: 検索欄（上部）
    actions:
      - text:
        summary: 入力が 300ms 止まるか変換が確定すると絞り込みを送り、一覧が入れ替わる
        expect: {value: self}
  - id: Search
    name: 検索（キーボードのキー）
    by: label
    actions:
      - tap:
        summary: デバウンスを待たずに絞り込みを送り、キーボードが閉じる
  - id: browse.empty_view
    name: 該当なしの表示
    when: 0件のとき
```

これで**その画面に何があるか**は分かる。項目の候補出しはここから始める。ただし**アクションの `summary` をそのまま期待値にしない。**

- **1行の要約でしかない。** 何件で次を取りに行くか、エラーの文言は何か、境界でどうなるかは書いていない
- **実装に追いついている保証がない。** `mapctl.py check` の鮮度で分かる（後述）。ずれていてもフローは通る（自動確認は `expect` の観測点しか見ない）ので、**古い `summary` を信じると、違う期待で撮った証跡がそのまま通ってしまう**

**`files` に読むべきソースが並んでいる。名指しのときは、対象に決めた画面の `files` を必ず読む。** 期待値はそこで確かめる。**マップの操作を1つずつ項目にしただけの plan にしない** — マップに書いてあることしか確かめられず、マップに無い表示の分かれ目が1つも出てこない。

```bash
python3 $R check --repo $M    # 「実装のほうが新しい」と出た画面は特に、必ず読む。dead の ID を押す・見る項目はフローが落ちる
```

- **見るだけの要素（`actions` の無い要素）も見る。** セクションの見出し、0件の表示、エラー時の再読み込みボタンなど。操作は無いが確認項目にはなり、plan の `see:<id>` で指せる。**`when` の付いたもの**（`0件のとき`、`通信エラーのとき`）は到着時点の状態で表示が分かれるもので、現在のデータでは踏めないことが多いので「一時コードが要る」と書く
- **状態を変える操作は、`summary` を読んで押してよいかを決める。** フォロー、登録、削除、設定の切り替えのように、アカウントやデータに残る変化は `summary` に書いてある。観点に関わらないなら押す項目を立てない。押すなら、起動し直しても戻らない変化をどう扱うか（後述「起動し直しても戻らないもの」）まで考える
- **`summary` をそのまま項目文にもしない。** `summary` は「何が起きるか」で、項目は「何が確認できたか」。静止画1枚で判定できる形に直す
- **名指しのときは、読んだコードから「データの形で表示が変わる箇所」を拾う。** 差分から立てるときと同じもの（「差分から」の該当箇所）で、`if` / `switch`、空のとき・0件のときの表示、`lineLimit` や切り詰め、配列を繋ぐ表示、数や日付の書式、画像が無いとき。マップの `elements` には出てこない。拾った箇所は項目にする（多くは `pick`。「タグが複数付いた行」）。いまのデータで踏めなければ「一時コードが要る」項目にする。外すかどうかはユーザーがレビューで決める
- **`when` の付いた表示も、データに依らずに作れるなら踏む。** 「0件のとき」は一致しない語を `"input"` で打てば出る。「一時コードが要る」と書くのは、いまのデータや通信では作れないもの（通信エラー、特定のアカウント状態）だけ
- **要素を全部項目にしない。** 網羅が目的ではない。言われた観点に関わるものに絞る。全部並べると証跡が膨らんで読まれなくなる。**絞るのは差分が無いときだけ** — 差分があれば、範囲は差分が決める

## どちらの入口でも守ること

- 番号付きの一覧にし、**1項目 = 1つの観測可能な結果**
- **項目はテストケースにまとめる。ただし、まとめるのは前の項目に依るときだけ**（前の項目の結果を当てにする、どこから来たかで結果が変わる）。それ以外は1項目ずつ別のテストケースにする（基準と書き方は手順3）
- **静止画1枚で判定できる形に書く。** 証跡はスクリーンショットなので、アニメーションの方向や遷移中の見た目は撮れない。「左からスライドして入る」ではなく「タブバーが隠れる」「戻るボタンが出る」のように、結果として残る状態で書く
- 現在のデータでは踏めない項目（課金プラン限定、特定のアカウント状態、エラー表示）も**plan の項目として立て**、報告の「一時コードが要る項目」に番号と、何を仕込めば出るかを書く。仕込むかどうか・仕込むのは呼び出し元の仕事。**踏めないことを理由に項目から外さない**
- 複数端末を見る場合も**端末ごとに項目を分けない。** 同じ項目を各端末で撮る
- **人が観点を言っていたら、必ずその項目を含める。** 差分にもマップにも現れないので、落ちやすい。差分があるときは、差分から立てた項目に**足す**
- **画面は `from` に書く。`title` に画面 id を入れない**（`browse: …` や `… [browse]` にしない）。撮った画面は manifest.py が `screen` に入れ、レビューでは `from` と `screen` が読まれる

## データに依る値は、決めない

**仕様はコードから読む。** 何が起きるか（デバウンスが 300ms、検索キーでキーボードが閉じる、プレースホルダが変わる）は `files` のソースに書いてある。

コードから出ないのは**いまどんなデータが入っているか**だけ。割れ目は1つ。

| | 例 | どうするか |
|---|---|---|
| **データに依らない** | 一致しない語、空文字、固定の業務値 | 打つ文字なら `"input": 値` でそのまま書く |
| **どれでもよい1つ** | 行を開いて、詳細が行と一致するかを見る | パターンの要素（ID の末尾が `*`）を**何も添えずに** `do` に書く。スクリプトが画面に見えている1件目を押す |
| **データに依る** | 実在する値で絞る、条件に合う行を選ぶ、作ったものを探す | 打つ文字は `"runtime": true`、どれを押すかは `"pick": 条件`。**例外なし** |

```bash
"do": [{"op": "text:browse.search_field", "runtime": true}]            // 打つ文字を実行時に決める
"do": ["tap:browse.book_row.*"]                                         // 画面に見えている1件目を押す
"do": [{"op": "tap:browse.book_row.*", "pick": "著者が複数いる作品"}]    // 条件に合う行を実行時に選ぶ
```

値はフローに焼き込まれず、撮影のときに決まる。条件の無い選択は `run_flows.py` が画面を読んで機械的に選び、`runtime` と `pick` は呼び出し元が画面を見て埋める。焼き込むと、データが変わったときに**古い値で黙って走る。**

- **自分で値を決めに行かない。** シミュレーターを触る手段は無い。着いた画面を見ないと決まらないものを事前に決めようとすると、**結局アプリを一通り操作することになる**
- **データソースを引かない。** API、DB、固定データのどれも。引くと、アプリが実際に持っているものとずれる（ページング、キャッシュ、別の絞り込み）
- **どれでもよいなら `pick` を付けない。** 付けると撮影がそこで止まり、呼び出し元が選ぶことになる。**どれを選んだかは期待の側で関係にする**（「タップした行の品名が詳細と一致する」）。選ばれた値はマニフェストの `devices.<端末>.picked` に出るので、判定する側が読める
- **`pick` の条件は、画面のダンプを見て選べる文で書く。** 選ぶ側が持っているのは、その時点のダンプと条件だけ。画面に出ていないこと（「貸出回数の多い本」）では選べない
- **`pick` はパターンの要素にだけ付く。** パターンでない要素に付けると manifest.py が止まる。**`tap` に `runtime` は付けられない**（これも止まる。どれを押すかは `pick` で言う）
- **特定の1つを名指しするなら ID まで書く**（`tap:browse.book_row.吾輩は猫である`）。呼び出し元がその1つを名指ししたときだけ。自分で選ぶならデータに依るので `pick`

**スクロールは書かない。** 押す前・見る前に、フローが必ず見えるまでスクロールする（`scrollUntilVisible`）。画面外の要素を確かめたいだけなら `see:<id>` で指す。スクロールそのものに結果がある操作（ページ送り）は、マップの `gestures` にあるものを `scroll:down` で指す。

## 期待は、証跡の中で確かめられる関係で書く

打つ文字が実行時に決まる以上、**結果の値を先に書けない。** 書けたとしても、データが変われば嘘になる。

```
書かない: 「李箱」で絞ると 6 件になり、先頭は「BOITEUX ・ BOITEUSE」
書く:     入力欄に出ている語を含む項目だけが並ぶ
```

判定する側は**証跡とダンプを全部読む**ので、この形なら確かめられる。打った文字もダンプの入力欄に出る。

- **画面をまたぐ突き合わせも関係で書く。** 「タップした行の品名が、詳細の品名と一致する」。どちらのダンプにも出ているので確かめられる
- **変更が言っている結果を、期待から落とさない。** 「検索キーを押すと確定してキーボードが閉じる」なら、確定（絞り込みの結果）とキーボードの両方が期待に要る。確かめやすいほうだけ残して、残りを「中身は関係ない」と外さない
- **値を固定にするときも、その値で出る結果で確かめる。** 一致しない語（`"input": "zzzz"`）で打つなら、該当なしの表示（`see:list.empty_view`）が出ることを期待にする。固定の値は結果を読みやすくするためのもので、結果を確かめないためのものではない
- **画面に出ないものを期待にしない。** 件数を出す要素が無いのに「6件になる」と書いても確かめようがなく、判定する側がデータソースに逃げることになる

**踏めないものは無理に踏まない。** エラー表示や特定のアカウント状態は、現在のデータでは出せないことが多い。**項目として立て、「一時コードが要る」と書いて返す**（仕込むのは呼び出し元）。

## テストケースと項目

- **plan はテストケース（`cases`）の集合。項目は必ずどれかのテストケースに属する。** テストケースは1つの機能を確かめるまとまりで、項目は1枚撮って1つ判定する単位。1項目だけのテストケースでよい
- **テストケースの中の項目は、前の項目に依存してよい。テストケースどうしは依存しない。** **別のテストケースに分けたら、前のテストケースが何を残したかを当てにしない**
- **同じテストケースに入れるのは、次のどちらかに当たるときだけ。** どちらでもなければ、1項目ずつ別のテストケースにする
  1. **後ろの項目の期待が、前の項目の結果を指す**（打った語で絞られた一覧から行を開く、詳細で見たものが一覧と一致する、開いたものが履歴に載る、戻ると開いた行が見えている）
  2. **後ろの項目の結果が、どこから来たかで変わる**（戻り先、戻るボタンの有無、閉じたあとの画面）。同じ画面でも、一覧から push で来たか、別のタブやショートカットから来たかで画面の積み重なりが変わる。差分がその遷移に関わるなら、経路を固定する — `from` までの経路は manifest.py が選ぶので、`from` だけではどこから来たかを確かめたことにならない。来る操作の結果も撮って確かめるなら前の項目にし、そうでなければ来る操作を `do` の先頭に書いて1項目にする（`from: browse`、`do: [行をタップ, 戻る]`）
- **不必要にまとめない。** 「一覧から詳細を開ける」と「詳細から前の画面に戻れる」は、戻り先の期待が「前の画面に戻る」だけなら別のテストケースでよい。同じ画面の項目だから、同じ機能だから、はまとめる理由にならない。まとめると、途中の項目が落ちたときに後ろの項目も撮れず、探索に回すときもまとめて回ることになる
- **来る操作（「行をタップして詳細へ」）を項目にするのは、その遷移そのものを撮って確かめるときだけ。** 詳細の中のもの（図書カードのリンク、関連作品）を確かめるだけなら、`from` を詳細にした1項目のテストケースにする。詳細までの経路はスクリプトが繋ぐ。特定の作品の詳細から始めたいなら、行のタップを `do` の先頭に書く。手前に「詳細を開く」項目を置くと、確かめていない遷移の証跡が1枚増える
- **同じ操作・同じ期待の項目を、テストケースごとに繰り返さない。** 「行をタップすると詳細に移る」を確かめるのは1回でよい。ほかのテストケースで詳細から始めたいなら `from` に書く。繰り返すと、同じ行を押した同じ証跡が並ぶだけになる
- **まとめたら、テストケースの `title` にまとめた理由が読めるように書く**（「一覧から開いた詳細から戻ると、開いた行の位置に戻る」）。「一覧から詳細を開き、戻れる」のように項目を並べただけの題だと、分けてよいのか読めない
- **テストケースは、始まる状態を自分で言い切る。** 始める画面は最初の項目の `from`、前提はその `when`。前にどのテストケースが走ったかで結果が変わるなら、分け方が間違っている
- **前の項目を期待の中で指すなら、その項目に `id` を付けて `{id}` で書く**（上の例の `{open}`）。「項目2と同じ」のように番号で書かない — レビューで並べ替えたり消したりするとずれる。指せるのは同じテストケースの中の、自分より前の項目だけ（manifest.py が確かめる）。マニフェストでは証跡の名前に展開される
- **テストケースの `title` は、何の機能を確かめるまとまりかを書く。** レポートの見出しになる。1項目だけなら項目の `title` と同じでよい
- **`cases` の並びがそのまま証跡の連番とレポートの順になる。** 見せたい順に並べる。連番（`test_01`, …）はテストケースをまたいで通しで振られる

## 項目の書き方

- **1項目＝ `from` から `do` を順に叩いて1枚。** 項目が持つのは**どこから何を確かめるか**だけで、**そこまでの経路は書かない。** 前の項目が終わった画面から `from` までは manifest.py が計算して繋ぐ（すでに居れば何もしない）
- **`from` は操作を始める画面。** 撮る画面ではない。「行をタップすると詳細に移る」なら `from` は `browse` で、`do` が `tap:browse.book_row.*`
- **自動で出るダイアログそのものを確かめるなら、`from` にその画面を書く。** 画面マップでどこかの画面の `auto_shows` に並んでいる画面（レビュー依頼、お知らせ）。manifest.py は出る先の画面まで行って、閉じずに出るまで待つ。ふつうの項目では、同じダイアログは出ていたら閉じられる。**出る条件はテストケースの前提。** 起動したときに出るものは、テストケースに `launch: true` を付ける（後述）。起動回数やデータで出るものは、待っても出ないと落ちる。`launch` / `clear_state` で作れなければ「一時コードが要る」と書いて返す
- **`do` は `from` から撮る地点までの操作を順に書く。** 確かめる操作の手前で状態を作る準備（語を打ってから検索キーを押す、特定の行を開いてから「読む」を押す）も並べてよい。撮るのは最後の操作のあとの1枚なので、`title` と `expect` は最後の操作の結果を言う。遷移する操作も書いてよい（行き先はマップの `expect` の `screen` で追う）。**確かめたい操作を経路計算に任せない** — 「戻るボタンで戻る」を確かめたいのに `from` を戻り先にすると、どの操作で戻ったかが manifest.py の選択になる
- **着いた状態を見るだけの項目は `do` を空にする**（「一覧が出る」など）。**画面の中の特定の要素を見る項目は `see:<id>`**（「下の方に関連作品が出る」など）。フローが見えるまでスクロールして、その要素があることを確かめてから撮る
- **撮る前に、見たい状態になるのを待つ要素が要るなら `see` を足す。** 操作の `expect` が操作の前から出ている要素（入力欄の値など）を指していると、フローは待たずに撮る。検索キーで確定する操作もこれに当たる（`expect` は入力欄の値）ので、絞り込まれた行を `see` で待ってから撮る。絞り込みなら `{"op": "see:browse.book_row.*", "input": "猫"}` で「その語を含む行」が出るまで待つ（打つ語を `runtime` で決めるなら、`see` にも `"runtime": true` を付ける。行が含む語は撮るときに決める。**打った語と同じとは限らない** — 作者で絞り込めば、行の ID は作品名）。**ただし、その行が操作の前から出ていると待たずに通る**ので、打つ語は操作の前の画面に出ていない行を選ぶ
- **アプリの外（`external`）のページを見る項目は、`see:text:<文言>` で外のページの文言を待つ**（`"do": ["tap:detail.card_link", "see:text:図書カード"]`）。外はマップに無いので文言で待つしかない。**アプリの中では使わない** — 文言はローカライズや表記揺れで壊れる。ID で書ける
- **入れる値の決め方は `do` の操作に添える。** 打つ文字は `{"op": 操作id, "runtime": true}`（撮影時に決める）か `{"op": 操作id, "input": 値}`（データに依らない値だけ。一致しない語など）。パターンの要素は、条件があるときだけ `{"op": 操作id, "pick": 条件}`。値の要らない操作は操作idの文字列のまま
- **`from` までの経路の途中でパターンの要素を押すときも、画面に見えている1件目になる。** どの行を開くかを気にするなら、それは確かめる操作なので `do` に書く（`from` を一覧にして、行のタップを `pick` 付きで並べる）
- **子の要素（マップの `children`。横スクロールの中、カードごとのボタン）は、親の中で操作する。** 親を縦に寄せて、子が見えるまで親を送るのはスクリプトの仕事で、書くのは操作だけ（`see:recommend.more` だけで、末尾まで送って確かめる）。パターンの親のどれの中でするかは、何も添えなければ画面に見えている1件目。**特定の親で確かめたいときだけ `in` を添える** — 名指しなら `{"op": "tap:recommend.more", "in": "recommend.carousel.9"}`、データに依るなら `{"op": "see:recommend.more", "in": {"pick": "10件に満たないカテゴリー"}}`（`pick` と同じく撮影がそこで止まり、呼び出し元が選ぶ）
- **件数（「このカルーセルに10件」）は期待にしない。** 1回のダンプには画面付近の3〜4件しか出ず、証跡からも数えられない
- **項目の前提は `when` に書く。** マップの `when` の文言を**そのまま**写す（`["ログイン中"]`）。manifest.py は意味を読まず、文字列が一致するかだけを見る。要るのは2つ
  - **条件つきの要素**（`when` のある要素）を、`from` までの経路で通るとき。無ければ manifest.py が「条件つき」と言って止まる
  - **結果が分かれる操作**（`expect` が `when` つきのリスト）を `do` で押すとき。どちらの枝を確かめる項目なのかを書く。無ければ止まる
- **`when` を書いても、その状態は作られない。** 経路と期待の枝を選ぶだけで、アプリがその状態にあるかはシミュレーター次第。いまの状態で踏めないなら、ほかの踏めない項目と同じく「一時コードが要る」と書く
- **アプリの外に出る操作**（`expect` が `external`。Safari、App Store など）は、フローが確かめない。その操作で終わる項目は自動確認が付かない（`checked` が空）が、**外に居るまま撮る**ので、外で何が開いたか（Safari で図書カードのページが開いている）を期待に書ける。外のページの読み込みは待たないので、読み込み前が写ったら撮り直しになる。途中で外に出る項目は、フローがその場でアプリに戻す
- **経路が組めなかったテストケースは `explore` にする。** 1項目でも組めなければ、そのテストケースごと。manifest.py が返した理由を `explore` の値にそのまま書く。探索で撮るかマップを作るかは呼び出し元が決める（手順4）。**マップが無いときは全テストケースが `explore`** で、mapctl.py は叩かない
- **準備のためだけに項目を立てない。準備の操作は `do` に並べる。** 項目にすると、撮る必要のない証跡が1枚増える。さらに、準備で起きた食い違い（打った語の絞り込みが期待と違う）が、それを準備に使ったすべての項目で NG に数えられ、1つの原因が何件もの NG に見える
- **画面に着くためだけの移動は `do` に並べず、`from` に書く。** どの経路で来てもよいなら、経路は manifest.py が計算する。`do` に並べるのは、状態を作る準備と、来る経路を固定したいとき（基準2）だけ
- **`path` を別に叩かない。** `manifest.py` の標準出力が走るフローと同じ実行から出た経路で、別に叩くと食い違う余地ができる

**plan は1つにする。** 分けると連番が振り直されて証跡の名前がぶつかる。

## `relaunch_after` は後に残す側が付ける

テストケースは、前のテストケースが終わった画面から続けて走る（そこから `from` まではスクリプトが繋ぐ）。**このテストケースが、後のテストケースの操作を変えてしまう状態を残すときだけ** `relaunch_after: true` を付ける。終わったらアプリを起動し直し、次のテストケースは起動した直後から始まる。

**付けるのは残した側。** 何を残したかは自分の操作なので分かる。後ろのテストケースは、自分の前に何が来るかを知らない（並べ替えられることもある）。

- **次に並べたテストケースを見て決めない。** 「次のテストケースは同じ欄に打ち直すから害が無い」で外さない。後ろに何が来ても崩れないかで決める — 並べ替えられることも、別の plan に使い回されることもある。**plan の最後に置いたテストケースも同じ**（「後に続くテストケースが無い」で外さない）。次が「一覧の1件目をタップ」なら、絞り込まれた行を押し、開いたままのキーボードが画面を隠す
- **スクリプトが消すものがあっても、残るものを見る。** 打つ前の `eraseText` が消すのは入力欄の文字だけで、絞り込みの結果と開いたキーボードは残る

| 付ける | 例 |
|---|---|
| 入力や絞り込みが残る | 検索欄に語が残ったまま、次のテストケースが一覧の行をタップすると、見えている1件目が絞り込まれた行になる |
| キーボードやシートが開いたまま | 次の項目の画面の下半分が隠れて撮れない |
| 画面の積み重なりやスクロール位置が残り、次の経路が変わる | 深い画面から戻り切れない、上にある要素が画面外にある |

- **フローの切り方のために付けない。** 落ちたときの巻き添えを減らすため、確認の軸が変わるから、といった理由は実行の都合で、テストケースが持つものではない
- **残さないなら付けない。** 付けるたびに起動と経路のぶんが乗る
- **アプリの外（Safari など）に出て終わるだけなら付けない。** アプリの中には何も残っていない。どのテストケースが次に来ても、スクリプトがアプリを前面に戻して（終了させずに）から経路を繋ぐ。`relaunch_after` を付けると、戻すだけで済むところを、終了させて起点から歩き直すことになる
- **項目には付けられない。** テストケースの途中で起動し直すと、前の項目を当てにしている項目の前提が消える。起動し直したいところで切れるなら、そこでテストケースを分ける

## `launch` は起動そのものを確かめるときだけ

**起動したときの表示や動き自体を確かめるテストケースには、`launch: true` を付ける。** そのテストケースはアプリを起動し直してから始まる。起動するとお知らせが出る、前回開いていた画面に戻る、起動時にログイン画面が出る、など。

```json
{"title": "起動するとお知らせが出る",
 "launch": true,
 "items": [
   {"from": "notice_sheet",
    "title": "起動するとお知らせが出る",
    "expect": "お知らせのシートが出て、題と閉じるボタンがある"}]}
```

**`relaunch_after` とは別のもの。** `relaunch_after` は「後に状態を残すので片付ける」で、残した側が付ける。`launch` は「起動が確かめる中身の一部」で、確かめる側が付ける。

- **きれいな状態から始めたいだけなら付けない。** 前のテストケースが状態を残しているなら、直すのはそちらの `relaunch_after`。`launch` を付けて済ませると、同じ状態を踏むほかのテストケースが守られない
- **起動しても出る条件が揃うとは限らない。** 起動回数やサーバーの配信で出るものは、起動し直しただけでは出ないことがある。作れなければ「一時コードが要る」と書く

## 起動し直しても戻らないもの

起動し直して戻るのは**アプリのメモリ上の状態だけ**（入力、絞り込み、画面の積み重なり、キーボード）。**登録・削除・フォロー・設定の切り替えのように、サーバーや端末に残る変化は戻らない。** `relaunch_after` を付けても後ろのテストケースは守られない。`clear_state` は端末側を消すが、ログインも消える。

データを変えるテストケースは、次のどれかにする。

- **元に戻す操作を、テストケースの最後の項目にする**（登録したら解除する）。解除も確かめる項目になる
- **変えたデータを報告に書く**（「作成したデータ」）。元に戻せないときは必ず
- **後ろのテストケースの期待を、データに依らない関係で書く**（「タップした行と詳細が一致する」）。件数や特定の行を当てにしない

# 4. 組めなかった項目は理由ごと返す

manifest.py は理由を返して終了コード 2 で終わる。**その文言をそのまま報告に載せ、その項目のテストケースに `explore` を付けて理由を書く。** 残りのテストケースで叩き直し、組めたところまでのフローは出しておく。

```
[2] (test_05) goto settings: 画面 settings がマップに無い。screens/settings.yaml を作る必要がある
```

- **マップの穴**（未マップの画面、`in_tree: false`、`expect` の `screen` の先が無い）は、**経路が組めない項目として理由つきで返す。** 探索で撮るかマップを作るかは**呼び出し元がユーザーに選んでもらう**ので、どちらかに決めて返さない。**その画面に依存している項目をまとめて挙げる** — 1画面のせいで何項目が影響を受けるかで、判断が変わる
- **呼び方の間違い**（`do` の名前が違う、`text` の値が無い、`tap` に `runtime`、パターンでない要素に `pick`）は自分で直す。`screens/<画面id>.yaml` を読み直せば分かる
- **「この画面にあるのは 〜」と返って、押したい要素がその中に無いなら、呼び方の間違いではない。** 差分やコードにその UI があるならマップの穴なので、そのテストケースを `explore` にする（「差分から」の最後）。並んでいる別の ID に書き換えない
- **前提が足りない**（「条件つき（when: 〜）」「結果が分かれる」）ときは、その項目がどの状態を前提にしているかを決めて `when` に書く。マップの文言をそのまま写す。どの状態でも確かめたいなら、前提ごとに項目を分ける
- **フローを手で書いて辻褄を合わせない。** マップが実装と違うなら、それは screen-map の仕事として報告する情報であって、ここで埋めるものではない

# やらないこと

- **レビューを受けること** — 返すのは案。ユーザーと話すのは呼び出し元
- **シミュレーターを操作すること** — 撮るのは呼び出し元（`run_flows.py` と sim-driver）
- **コードの編集** — 一時コードが要る項目は「要る」と書くだけ
- **OK/NGの判定・レポートの生成**
- **画面マップの作成・修正** — 穴は報告する。埋めるのは screen-map スキル
