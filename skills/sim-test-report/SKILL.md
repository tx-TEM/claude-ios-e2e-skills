# シミュレーター動作確認レポート

シミュレーターでの動作確認の各ステップを撮影し、HTMLレポート・1枚画像（PNG）・スクリーンショット一式をデスクトップの1フォルダに出力して届ける。HTMLは画像をbase64で埋め込んだ単一ファイル、PNGはHTML全体を1枚に描画したもので、PRコメントにそのまま貼れる。

## 手順

### 0. テストケースを作ってレビューを受ける

シミュレーターを操作する前に、確認項目の一覧をユーザーに提示してレビューを受ける。合意してから実施に入る。

- 変更で壊れ得る箇所を起点に列挙する。「移管でローカライズを差し替えた」「参照方法を変えた」など、変更の中身から逆算して導線を選ぶ
- 番号付きの一覧で出し、1項目 = 1つの観測可能な結果にする
- **静止画1枚で判定できる形に書く。** 証跡はスクリーンショットなので、アニメーションの方向や遷移中の見た目は撮れない。「左からスライドして入る」ではなく「タブバーが隠れる」「ナビゲーションバーに戻るボタンが出る」のように、結果として残る状態で書く
- 現在のデータでは踏めない項目（課金プラン限定の機能、特定のアカウント状態など）は、この時点で「一時コードで再現する」と明記して合意を取る
- **iPadも対象にするかをここで決める。** どのシミュレーターを使うかは手順1で起動中のものから選ぶ。レイアウトが分岐する変更（サイズクラス、Split View、ポップオーバー、レギュラー幅での段組み）は iPad を対象に入れる価値が高い
- 複数端末を見る場合も、テストケースは端末ごとに分けない。同じ項目を各端末で撮り、レポートでは1セクションに並べる

#### 過去のケースフローで済むか見る

**ケースフローのディレクトリ**に、今回の導線をそのまま通せるフローが残っていないかを見る。撮り直し、同じテストを2台目の端末で撮る、といった場合はここで済む。

**`common/` は判定の対象ではない。** あれは起動や画面遷移といった断片で、単体では確認項目の導線を通さない。`flow-author` が使う材料であって、足りているかを数えるものではない。

あわせて `shared_dirs` の `README.md` を読む。「Maestro が動かない画面」に載っている区間は、フローにできないので手で操作する側に回す。

新しい変更の確認なら、ほぼ常に次へ進むことになる。

#### 足りない導線は、撮影前に flow-author で用意する

**`flow-author` を呼ぶのが既定。** 過去のケースフローで済む場合だけ省ける。

**フローが無い導線を、そのまま撮影に投げない。** sim-driver が走りながら導線を探すことになり、探索と撮影が混ざる。

`flow-author` に次を渡す。

- テスト内容（確認項目の一覧）
- 対象アプリのリポジトリのパス、bundle id
- 共有フローのディレクトリ、作業用ディレクトリ、対象デバイスのUDID

**sim-driver と同時に走らせない。** 検証でシミュレーターを使うので取り合いになる。撮影の前と後にだけ呼ぶ。

返ってくるのは「導線の棚卸し / 作ったフロー / フローにできなかった区間 / 気づいたこと」。

**棚卸しの表をユーザーに提示して、合意を取ってから撮影に入る。** どの画面のどのボタンを押す手順になっているかが、出どころ（ファイル名と行番号）つきで並んでいる。意図と違う画面を経由していないかは、テストケースの文面からは分からない。ここが導線に対するレビューの場になる。

**この結果から、項番ごとの対応表を作る。** これが sim-driver に渡す中心的な情報になる。

```
項番1〜4   cases/<日付>-pre-state.yaml
項番5      手で操作（READMEの「動かない画面」に該当）
項番6〜8   cases/<日付>-<テーマ>.yaml
項番9〜12  手で操作（flow-author が確定できなかった区間）
```

**全項番に指定を付ける。** 空欄を残したまま撮影に入らない。判断は呼び出し元が持ち、sim-driver には持たせない。

確定できない区間が多くて `flow-author` が途中で止まった場合は、テストケースの書き方か対象の導線を見直す。無理に進めさせない。

#### 撮影中にどこでLLMへ切り替わるかは、事前に決めない

用意が済んでいる前提で、撮影中にフローが落ちたときの話。

**どの区間が落ちるかを事前に判定しない。** まず走らせ、落ちたらその区間だけLLMに切り替える。

**1つの導線の中で切り替えてよい。**

```
A → B    Maestro
B → C    LLM（Cで落ちた、または README に載っている）
C → D    Maestro
```

`launchApp` を含まないフローは、その時点で開いている画面から続きを実行する。区間の切り方に制約はない。

**これは準備を省く理由にはならない。** 落ちたときの切り替えは、用意したフローが想定外の画面に当たったときの手当てであって、用意しないことの代わりではない。

### 1. 撮影する

撮影に入る前に、いま起動しているシミュレーターを確認する。

```bash
xcrun simctl list devices booted
```

**その一覧から使う端末を選び、「iPhone 11 Pro (iOS 17.5) と iPad Air 13-inch (M3) (iOS 26.1) で撮ります」と機種名・OSバージョンを挙げて提示してから撮影に入る。** ここで挙げた内容がそのままレポートの確認環境になる。

手順0で対象にした端末が起動していない場合、1台も起動していない場合、同じ機種が複数あってどれか決まらない場合は、ユーザーに確認する。**勝手に起動したり、起動中の別の端末で代用したりしない。**

#### フローの場所を解決する

置き場所は `skills/sim-test-report/config.json` で決める。**共有する部品と、確認ごとのフローで置き場所が違う。**

```json
{
  "maestro": {
    "enabled": true,
    "shared_dirs": [
      "${app_repo_path}/maestro",
      "${skill_dir}/.cache/${app_repo}"
    ],
    "cases_dir": "${skill_dir}/.cache/${app_repo}/cases",
    "apps": {}
  }
}
```

- `shared_dirs` — **共有する部品**（`common/` と `README.md`）を探す場所。上から見て最初に存在したものを使う
- `cases_dir` — **確認ごとのフロー**を置く場所。常に端末ローカル
- `apps` — アプリ個別の上書き。`{"MyApp-iOS": {"shared_dirs": ["~/somewhere/flows"]}}` のように書く
- `enabled` — `false` にすると Maestro を使わせず、sim-driver に全部任せる

置き換わる変数は3つ。`${app_repo_path}`（対象アプリのリポジトリの絶対パス）、`${app_repo}`（そのディレクトリ名）、`${skill_dir}`（このスキルのディレクトリ）。`~` は展開し、相対パスはこのリポジトリのルートから解決する。

同じディレクトリに `config.local.json` があれば、その内容を上書きとして重ねる（gitignore 済み）。

**解決した絶対パスを2つとも sim-driver に渡す。** `enabled` が `false` のとき、`shared_dirs` がどれも存在しないときは渡さない。

#### sim-driver に渡す

- テストケース一覧（手順0で合意したもの、項番つき）
- **対象デバイスのUDID**と、ファイル名に使う端末名（`iphone` / `ipad` など）
- 証跡の出力先ディレクトリ。`~/Desktop/sim-test-report-<テーマのslug>/shots/`。呼ぶ前に `mkdir -p` で作っておく。リポジトリ内には作らない
- 前提条件（アカウント、必要なデータ、事前設定）
- **共有フローのディレクトリ**と**ケースフローのディレクトリ**（無ければ渡さない）
- **項番ごとの対応表**（手順0で作ったもの。全項番ぶん）
- **対象アプリのリポジトリのパス。** 画面に出ている文言から実装を引けるようになり、迷ったときにスクリーンショットを撮らずに位置を特定できる

**プロンプトに操作手順を書き下さない。** 渡すのは「何を撮るか」であって「どう操作するか」ではない。タップの段取りを細かく書くと、sim-driver は自分の既定よりプロンプトを優先し、Maestro で動く画面まで手動でなぞる。**対応表に「手で操作」と書いていない画面を、同じタブ・同じ機能だからと巻き込んで手動に回さない。**

証跡の撮り方も指定しない。Maestro の `takeScreenshot` と `xcrun simctl` のどちらを使うかは sim-driver が操作手段に合わせて決める。

複数端末を見る場合は端末ごとに呼ぶ。1回のサブエージェントで2台を行き来させると、座標系の切り替わりで誤操作が増える。

返ってくるのは「項番 / ファイル名 / 観測した事実」だけで、OK/NGの判定は含まれない。**判定は自分で証跡PNGを読んで下す。** 写っている情報で判断できなければ、追加の観点を伝えて撮り直させる。

sim-driver の実行結果には、消費トークン・ツールコール数・所要時間が付いてくる。**これを控えておく。** 自分で走らせた `maestro test` の回数と所要時間も同様。手順3で出す。

連番はレポートで見せたい順にする。操作順と一致しなくてよいし、撮り逃した画面は後から撮り直させてよい。

#### 一時コード

確認項目がいまのデータやタイミングでは踏めない場合、一時的にコードを変えて再現してよい。**仕込みと revert は呼び出し元（自分）が行い、サブエージェントには撮影だけさせる。**

- 変更箇所に `// FIXME: 動作確認用の一時コード` と、本来の実装をコメントで残す
- 撮影後に必ず revert し、`git status` がクリーンであることを確認する
- 使った一時コードは全てレポートのfooterに書く（どのファイルの何を、どの確認項目のために変えたか）
- 一時コード入りのビルドで撮ったスクリーンショットは、そのセクションの説明にもその旨を書く

トーストやスナックバーなど短時間で消えるUIは、**撮る手段によって扱いが変わる。**

- **Maestro で撮る場合** — 一時コードは要らない。タップと撮影が同じプロセスで連続実行され、素の表示時間で間に合う
- **sim-driver が自分で撮る場合** — タップとスクリーンショットのツール往復が表示時間を超えて撮り逃す。表示時間を延ばす一時コード（例: `hideDelay` を60秒にする）を入れてから撮る

短命UIを含む項目は、**Maestro のフローを作る候補として優先度が高い。**

どちらの手段でも、撮れないことを「表示されない」と判断しない。

#### 撮り終えたら、フローのどこを残すか決める

撮影で使ったフローはケースフローのディレクトリに残っている。**そのうち再利用できる区間だけを `common/` に切り出す。**

1本のフローの中に、次も使う区間（起動、目的画面までの遷移）と、その確認限りの区間が混ざっている。**前者だけを抜き出して部品にする。** 粒度と書き方は `references/maestro-flow.md` に従う。

LLMが自分で操作して通した区間も、その時点で導線が確定している。またすぐ撮ることになりそうなら同じようにフロー化する。

**フローはスクリーンショットから起こさない。** 撮影の報告から分かるのは「どの画面をどの順で通ったか」まで。**確定した導線を手がかりに、コードでセレクタを裏取りしてから書く。**

**Maestro が落ちた画面があれば、`README.md` の「Maestro が動かない画面」に書き足す。** 次回は手順0でそれを読み、最初からLLMに回せる。

切り出しは**ユーザーに聞いてから**行う。レポートを先に届けて、切り出しは別途でもよい。

### 2. マニフェストを書いてレポートを生成する

セクション情報をJSONマニフェスト（`~/Desktop/sim-test-report-<slug>/manifest.json`）にまとめ、同梱スクリプトで生成する:

```bash
python3 <このスキルのディレクトリ>/scripts/build_report.py <manifest.json>
```

HTMLと同じ場所に、PRコメント貼り付け用の1枚画像（同名の.png）もデフォルトで生成される（headless Chromeを使用。不要な場合のみ `--no-png`）。

マニフェストの形式は `scripts/build_report.py` 冒頭のdocstringを参照。書く内容の指針:

- **title**: 「<変更内容> — 動作確認レポート」の形
- **meta**: Issue/PR番号、ブランチ名、確認環境（機種・OSバージョン）、実施日
- **sections**: レポートの本体。1確認項目 = 1セクションで、タイトルは「何が確認できたか」を言い切る形にする。説明には期待挙動と実際の観測結果を書き、変更前との差分（「変更前は〜だった」）があると読み手に親切
- **images**: 同じ項目を複数端末で撮った場合は1セクションに並べる。`{"src": "shots/iphone_02_toast.png", "label": "iPhone 11 Pro"}` の形。**labelは撮影した端末の機種名**で、metaの確認環境と1対1で対応が付く表記にする。OSバージョンはmetaに任せる。1枚だけなら `"image": "shots/01_foo.png"` でもよい
- **result**: 確認できたら "OK"。**複数端末を撮った項目は、全端末で確認できたときだけ "OK" にする。片方でもNGならセクション全体をNGとし、どちらがどう駄目だったかをdescに書く。** NGや保留があった場合も隠さずそのまま書く
- **footer**: 画面では確認できなかった項目の補足。コードで裏取りした内容、確認をスキップした理由

### 3. 届ける

SendUserFileでHTML（`display: "render"`＝その場でプレビュー）とPNG（`display: "attach"`＝PR貼り付け用）を送り、デスクトップのフォルダパスも伝える。画質を落として縮めるより、証跡として読めることを優先する。

あわせて**撮影にかかった内訳をユーザーに伝える。** レポートのfooterには入れない。

```
撮影の内訳
・sim-driver: <トークン> / <ツールコール数> / <時間>
・Maestro:    <回数> / 計<時間> / 実行中のLLM往復なし
※ テストケース作成・証跡判定・レポート生成の消費は含まない（計測手段が無い）
```

**総額としては書かない。** 呼び出し元の消費を取得する手段が無く、その部分が丸ごと抜けるため。注記を必ず添える。

## 注意

- テスト実行（xcode-bridge等）はシミュレーターのアプリを再インストールし、ログイン状態を消すことがある。動作確認とテスト実行を同じシミュレーターで行う場合は、先にその影響をユーザーに伝える
