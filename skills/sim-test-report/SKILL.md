# シミュレーター動作確認レポート

シミュレーターでの動作確認の各ステップを撮影し、HTMLレポート・1枚画像（PNG）・スクリーンショット一式をデスクトップのフォルダ（`~/Desktop/sim-test-report-<日付>-<テーマ>/`）に出力して届ける。HTMLは画像をbase64で埋め込んだ単一ファイル、PNGはそれを1枚に描画したもので、PRコメントにそのまま貼れる。

**レポートに載せる画像はファイルに残るもので撮る**（`xcrun simctl io` か Maestro の `takeScreenshot`）。シミュレーターMCPの screenshot は自分が見るためのもので、ファイルに残らない。

**往復の多い作業はサブエージェントに出す。** 1ターンのコストはその時点のコンテキストの大きさでほぼ決まるので、実装作業で膨らんだ文脈のまま往復すると、中身とほぼ無関係にターン数ぶんのコストが乗る。テストケース作り（`test-case-builder`）、探索での撮影（`sim-driver`）、判定（`evidence-judge`）、撮り直し（`retaker`）がそれにあたる。

**手順の途中で分岐に来たら、指している `reference/*.md` を読んでから進める。** 分岐ごとの書き方（ユーザーに出す2択の形など）はそこにあり、ここには無い。

**ユーザーに選んでもらうときは AskUserQuestion で聞く。** 本文に a) / b) を並べて書くと、返事が自由文になり、どれを選んだかを読み取り直すことになる。項目が複数あると、どの項目にどれを選んだかも読み違える。

- **1つの決めごとを1問にする。** 同じ理由で同じ扱いになる項目（1つの画面のマップが無いせいで探索になるテストケース、など）はまとめて1問。理由が違えば分ける。1回で聞けるのは4問まで、1問の選択肢は4つまで
- **question に、どの項目の話かを名前（`test_10`）で入れる。** 理由や根拠が長いとき（落ちたフローの行、判定の根拠と実装の場所）は、本文に書いてから聞く。question に詰め込まない
- **選択肢の label は短く、何が起きるかは description に書く。** 選んだあとに増える手間や、アプリ側の変更（別ブランチ・別PR）は description に明示する
- **勧める側があれば先頭に置き、label の末尾に「（おすすめ）」を付ける。** 勧める理由が無ければ付けない（探索で撮るかマップを作るかのように、ユーザーの時間や都合で決まるもの）

## 手順

### 0. テストケースを作ってレビューを受ける

シミュレーターを操作する前に、確認項目の一覧をユーザーに提示してレビューを受ける。合意してから実施に入る。

#### 呼ぶ前に決める

`test-case-builder` は会話を持たない。**届くのは、呼ぶときに書いた本文だけ**なので、次を先に確定させて、下の型で渡す。

- **ユーザーの指示は、原文のまま引用する。** 言い換えない・観点に書き直さない — 書き直すとこちらの解釈が混ざり、builder にとってはそれが指示のすべてになる。確認に関わる発言が複数あれば全部引く。欠けていると builder は止まる
- **差分。変更を確かめるなら「あり」と書く。** 範囲は `diffscope.py` が決める。今のブランチのコミットのうち、既定ブランチにも、ほかのオープン中の PR にも入っていないもので、コミットしていない変更も入る（作業ツリーまで）。積んだ PR の親や既定ブランチはこちらで調べなくてよい。自動の決め方が合わないと分かっているときだけ、ベースのブランチやコミットを添える。項目は差分から立つ。観点は差分に**足す**もので、差分の代わりにしない — 観点だけを渡すと、項目は観点どおりに立ち、観点に挙げなかった変更は確かめられないまま噛み合って見える
  - **変更と関係ない対象**（「一般的な機能をテストして」「さがす画面を一通り」）なら、差分は「なし」と書く
  - **変更の一部に絞る指示**（「このブランチのうち、詳細のボタンだけ見て」）でも、差分は渡す。絞り方はユーザーの指示の原文で伝わり、builder は範囲外の変更を項目にせず、報告の入口の行に「ユーザーの指示で範囲外: …」と書く。レビューで読み上げ、外したものをユーザーが見て合意できる
  - **どちらか迷ったら差分を渡す。** 渡して外したものは読み上げで見えるが、渡さなかった漏れはどこにも見えない
- **画面の動きを本文で説明しない。** マップとコードは `test-case-builder` がリポジトリから読む（アクセシビリティ ID もマップから取る）。こちらの要約を渡すと、要約に無いことが項目に上がらず、差分を読む理由も減る。**変更の意図**（なぜ変えたか、何を狙ったか）はコードから出ないので渡す
- **撮る端末とシミュレーター。** `xcrun simctl list devices booted` の一覧から `iphone` / `ipad` それぞれ1台を選び、UDID を控える（渡すときは `iphone=<UDID>` の形）。レイアウトが分岐する変更（サイズクラス、Split View、ポップオーバー）は iPad を入れる価値が高い。**対象が起動していない・同じ機種が複数あって決まらないときはユーザーに確認する。勝手に起動したり、別の端末で代用したりしない** — 全項目が合意と違う端末の証跡になる
- **証跡の出力先**（`~/Desktop/sim-test-report-<日付>-<テーマ>/`）と**対象アプリの bundle id**（`xcrun simctl listapps <UDID>`）
- **対象アプリのリポジトリのパス**。画面マップの有無はサブエージェントが見る（無ければ全項目が探索の plan で返る）

**本文はこの型で書く。自由作文にしない。** 欄を落とすと言い換えや書き漏らしが起きても気づけない。

```
ユーザーの指示（原文）:
> お気に入りを足したので、シミュレーターで動作確認して。詳細でボタンを押すと印が付くことは必ず見て

差分: あり                          （変更と無関係なら「なし」。起点を指定するなら「あり（ベース: feature-x）」）
変更の意図: よく見るアイテムに戻りやすくするため、詳細にお気に入りボタンを、一覧にその印を足した
リポジトリ: ~/Program/MyApp
bundle id: com.example.MyApp
端末: iphone=<UDID>
出力先: ~/Desktop/sim-test-report-favorite/
```

画面の動き・観点の書き直し・ID は書かない（下の「画面の動きを本文で説明しない」）。

**データに依る値は決めさせない。** 打つ文字は `"runtime": true`、条件で選ぶ行（押す・見る）は `"pick": 条件` で plan の `do` に未定のまま残し、撮影のときに埋める。`runtime` は打つ文字にだけ付く。条件が無ければ何も添えず、`run_flows.py` が画面に見えている1件目を選ぶ。事前に決めさせると、サブエージェントがアプリを一通り操作することになる。

**データソース（API、DB、固定データ）も引かせない。** 引いて期待を作ると、モックが間違っていれば期待も一緒に間違う。そのぶん**期待は関係で書く**（「入力欄に出ている語を含む項目だけが並ぶ」）。

#### 返ってきたものを読む

返るのは `<このスキルのディレクトリ>/.work/flows/<出力先の名前>/plan.json` と、そこから作った `manifest.json`。**案であって合意ではない**ので、ユーザーに出す前に自分で読む。

- **差分から立っているか。差分のファイルと見比べる。** 報告の「入口」の行が差分になっているかを見たうえで、`diffscope.py` の一覧（builder と同じ範囲）を自分で出し、画面に出る変更がどれかの項目になっているかを見る（ユーザーの指示で範囲外にしたものを除く）。項目に無い変更があれば、それを伝えて組み直させる。自分が実装で書いたものを思い出しながら見る — 観点に挙げなかった変更こそ漏れる

```bash
python3 <このスキルのディレクトリ>/scripts/diffscope.py <アプリのリポジトリ>
```

- **足したビュー・変えたビューなのに、データの形で表示が変わる箇所の項目が1つも無ければ、拾い漏れを疑う。** 踏めない分かれ目も「一時コードが要る」項目として立っているはず
- **「一時コードが要る項目」は、仕込むか外すかをユーザーに聞く。** builder は外さずに返す。外すと決めるのはユーザー。選択肢は「仕込んで撮る」（description に何を仕込むか）と「外す」
- **前提（`when`）のある項目は、撮る前に撮れるかをユーザーに聞く。** マニフェストの `preconditions` に、前提の文言ごとに項目の名前と両立しない前提（`rivals`）を manifest.py が集めてある。聞き方は下の「前提を聞く」
- **差分が無く、画面・機能を名指ししたときは、コードを読んだかを見る。** マップの操作を1つずつ項目にしただけに見えるなら、画面の `files` を読んでいない。組み直させる。アプリ全体（「一般的な機能」「一通り」）のときは、主な導線の疎通確認で粗くなるのを許容する
- **項目が変更と噛み合っているか。** 外していれば観点を伝えて組み直させる
- **選んだ画面が観点と合っているか。** 画面を取り違えてもフローは通るので、項目の画面idを読むのが唯一の歯止め
- **「候補が絞れなかった項目」は、自分で決めてから出す。** 実装を知っているのは自分
- **「マップに足す候補」は捨てず、**手順3の報告に持っていく
- **テストケースの分け方を見る。** 前の項目の結果を当てにしている項目（「一覧は前と同じ行のまま」「開いたものが履歴に載る」）が、別のテストケースに分かれていないか。分かれていると、並べ替えや探索への切り替えで前提が黙って消える。逆に、当てにしていない項目が1つのテストケースに詰め込まれていないか。まとめてよいのは、前の項目の結果を指すときと、どこから来たかで結果が変わるときだけ
- **`launch` が、起動そのものを確かめるテストケースにだけ付いているか。** きれいな状態から始めたいだけの `launch` は、画面マップの `leaves` の書き漏れを隠している
- **後に状態を残すテストケースの後始末は、マニフェストの `cases` の `after` を見る。** 後始末は画面マップの `leaves` / `reset` からスクリプトが決め、plan では指定しない。入力・絞り込み・セグメントの選択を残すテストケースなのに `after` が空なら、その操作にマップの `leaves` が書かれていない。「マップに足す候補」に挙げる（builder の報告にあればそれを使う）。アプリの外（Safari など）に出て終わるのは残る状態ではない。データを変えるテストケース（登録、削除）は、起動し直しても戻らないので、元に戻す項目があるか、作ったデータを報告に書くことになっているかを見る
- **トーストのようにすぐ消えるUIは、操作とその撮影が plan の同じ項目に入っているか確かめる** — 別の項目に分かれると、間にツール往復が挟まって撮り逃す
- **直すのは plan.json。** manifest.json は手で直さない — 次に manifest.py を叩き直すと消える。フローは run_flows.py が撮るときに組むもので、`.work/flows/` の yaml は流したものの記録（run_flows.py は読まない）。レビューでの1〜2箇所の手直しなら自分で直して下を叩き直し、項目の立て方から見直すときだけ呼び直す（**手順2の `RETAKE` のときは自分で直さない**）

```bash
python3 <このスキルのディレクトリ>/scripts/manifest.py \
  <このスキルのディレクトリ>/.work/flows/<出力先の名前>/plan.json <出力先> \
  --device iphone=<UDID> [--device ipad=<UDID>]
```

項目の名前は並び順（`test_01`, …）。証跡は `shots/<端末>/<名前>.png` に分かれる。**作業用のファイルはスキル側の `.work/flows/<出力先の名前>/` に置き、アプリのリポジトリの下に作らない**（誰も片付けない）。**出力先の名前は `sim-test-report-<日付>-<テーマ>`**（`sim-test-report-20260928-search`）。並べれば時系列になり、`.work/flows/` とダンプの置き場も同じ名前で分かれる。実行ごとに変え、同じ日に同じテーマでやり直すなら `-2` を足す。前の回と同じ名前にすると、前の回の判定と実行時の値を引き継ぐ。形が違えば manifest.py が警告を出す

- 直す先は2つある。**導線がテストケースに合っていないなら plan の `from` / `do`。マップが実装と違うなら screen-map の仕事**で、plan 側でマップのずれを埋め合わせない
- **フローが通ることはこの時点では確かめない。** 通らなければ撮影のときに分かる

**経路が組めなかったテストケース（plan で `explore` の付いたもの）があれば、探索で撮るかマップを作るかを AskUserQuestion で選んでもらう。勝手に決めない。** → `reference/unroutable.md` を読んでから書く

#### レビューに出す

**`manifest.json` の `cases`（テストケースと、その下の `items`）をそのまま読み上げる。組み立て直さない。** 撮る端末を最初に出す。

```
iPhone 17 Pro (iOS 26.5) で撮ります。

**キーワードで一覧を絞り込める**

2. キーワードを打つと入力が止まってから絞り込みが走る［さがす画面］
   - 操作: 検索欄に入力する（打つ語は撮るときに決める）
   - 期待: 入力欄に出ている語を、一覧に残っている行がすべて作品名に含む
3. 検索キーで絞り込みが確定する［さがす画面］
   - 操作: 検索キーを押す
   - 期待: キーボードが閉じている。一覧は test_02（キーワードを打つと…）と同じ行のまま
   - ⚠ 画面の自動確認なし。証跡だけで判定

→ ここでアプリを起動し直す

**一覧から詳細を開ける**

6. 一覧の作品をタップすると詳細に移る［詳細画面］
   - 操作: さがす画面で見えている1件目の行をタップする
   - 期待: 詳細画面の作品名が、タップした行の作品名と一致する
7. 書誌と関係者が出る［詳細画面］
   - 操作: なし（着いた状態を見る）
   - 期待: 作品名のほかに、書誌の情報と関係者の行が出ている

ユーザーの指示で範囲外: 並び替えの既定値（「検索だけ見て」）
```

- **ユーザーの指示で範囲外にしたものがあれば、項目の後ろに「ユーザーの指示で範囲外: …」と読み上げる。** 原文の一節も添える。外したものをユーザーが見て合意できるように
- **「一時コードが要る項目」は、その項目の行に「⚠ 一時コードが要る（何を仕込むか）」を付ける。** 仕込むか外すかをここで聞く
- **テストケース（`cases` の要素）ごとに、その題を見出しにする。** 1項目だけのテストケースも見出しを付ける。どこからどこまでが前の項目を当てにしている流れかが、ここで読める
- **各項目の題の後ろに、撮った画面（`screen`）の画面マップの `names` の先頭を［］で添える。** 画面 id は出さない。探索の項目（`screen` が空）は `from` の画面を添える。どの画面の項目かが読めるのが、画面の取り違えの歯止めになる
- **起動し直しは、マニフェストの `cases` から読み上げる。**
  - **`after.relaunch` が真のテストケースの後ろに「→ ここでアプリを起動し直す」と書く。** `after` は画面マップの `leaves` からスクリプトが決めた後始末で、`leaves` の文を理由に添える（「→ ここでアプリを起動し直す（入力欄の語と絞り込みの結果が残るため）」）。後ろのテストケースがどの状態から始まるかが読める。次の項目の操作には書かない
  - **`after.resets` があれば、そのテストケースの後ろに「→ ここで〜で戻す」と書く**（「→ ここでクリアボタンで戻す（入力欄の語と絞り込みの結果が残るため）」）。操作は画面マップの `name` で言う
  - **`launch` の付いたテストケースだけ、最初の項目の操作を「アプリを起動し直し、」から書く。** 起動が確かめる中身の一部なので、操作として読み上げる
  - 最初のテストケースの最初の項目にも書かない（撮影はいつも起動から始まる）
- **探索で撮るテストケース（`explore`）は、見出しの後ろに「（探索で撮る: 理由）」と添える。** 並びはその場のまま
- **各項目は `番号. 項目名` のあとに操作・期待・注記を箇条書きで並べる。** 並びを毎回そろえる
- **操作は必ず書く。** 空なら「なし（着いた状態を見る）」とこの文言のまま書く — 省くと、無いのか書き忘れか読めない。`runtime` は打つ語を撮るときに決める旨、`pick` は条件（「著者が複数いる作品の行」）と撮るときに選ぶ旨（`see` なら押さずに見る旨も）、条件の無いパターンの要素なら「見えている1件目」、`see` なら「〜が見えるまでスクロールする」、始める画面が撮る画面と違うなら呼び名で添える。「特定の1件で」のような指摘はここを見て初めて出る
- **期待は必ず書く。** 項目名に含めて省かない
- **前提（`when`）があれば「前提: ログイン中」と書く。** どの項目がどの前提かを読むため。撮れるかは、項目を読み上げたあとに前提ごとにまとめて聞く（下の「前提を聞く」）。項目の行に埋もれていると問いとして読まれない
- **`from` までの経路は出さない。** manifest.py が計算するもので、レビューの対象ではない
- **`checked` が空の項目にだけ、その項目の行に「⚠ 画面の自動確認なし」を付ける。探索の項目も `checked` が空なので付ける** — 探索にするかの問いで触れていても、項目の行からは外さない。何も待たずに撮るので、着いたことすら確かめていない。集計や問いで出すと、どの項目の話か読み替えが要る。多ければ確認として弱いことを伝える（`reference/unroutable.md` の末尾）

#### 前提を聞く

**マニフェストの `preconditions` が空でなければ、項目を読み上げたあとに、前提ごとに撮れるかを聞く。** `when` は経路と期待の枝を選ぶだけで、アプリをその状態にしない。シミュレーターがログインしているか、データがあるか、初回だけの表示が済んでいるかは、ユーザーにしか分からない。聞かずに撮ると撮影で落ち、retaker が「前提の状態が無い」と返してやっと分かる（撮影と撮り直しの時間が無駄になる）。

**聞くのは AskUserQuestion で、1つの前提を1問にする**（冒頭の「ユーザーに選んでもらうときは AskUserQuestion で聞く」）。

```
question: 「ログイン中」の項目（test_04, test_05）を撮る前に。シミュレーターはこの状態ですか？
header:   ログイン中
options:
  - その状態にしてある     — そのまま撮る
  - わからない、撮ってみる — そのまま撮り、落ちたら前提の状態が無いと見て聞き直す
  - 一時コードで作る       — <何を仕込むか>
  - 外す                   — この前提の項目を外す
```

- **question に前提の文言と項目の名前を入れる。** `preconditions` をそのまま使う（同じ文言は manifest.py が1つにまとめてある）。header は前提の文言を12字以内に縮めたもの
- **1回で聞けるのは4問まで。** 前提が5つ以上なら、呼び出しを分ける
- **「その状態にしてある」「わからない、撮ってみる」なら、そのまま撮る。** 落ちたら `reference/flow-failed.md` の「前提の状態が無い」で受ける。「わからない」は、状態がデータや API のレスポンスで決まっていて、ユーザーにも見分けられないとき。撮れたらそれで済み、落ちたらその前提の項目だけを、一時コードで作るか外すかで聞き直す
- **「一時コードで作る」の description には、何を仕込むかを書く。** 書けなければ選択肢に出さない。選ばれたら、仕込みと revert は `reference/temp-code.md` の流れで自分がやり、手順2で evidence-judge に「一時コード」として渡す
- **「外す」なら、plan.json からその項目を外して manifest.py を叩き直す。** 同じテストケースの後ろの項目がその項目の結果を当てにしているなら、一緒に外れることを description に書く。外したものは「ユーザーの指示で範囲外」と同じく、外したものとして読み上げる

**両立しない前提（`rivals`）が並んでいたら、ほかの前提より先に1問で聞く。** 1台のシミュレーターは「ログイン中」と「未ログイン」に同時になれず、`run_flows.py` には撮影の途中で止まって状態を切り替える仕組みも無い。返事で次の問いが変わるので、ほかの前提とは別の呼び出しにする。

```
question: 「ログイン中」（test_04, test_05）と「未ログイン」（test_06）は、1台のシミュレーターでは同時に満たせないので、同じ撮影では両方は撮れません。どちらをどうしますか？
header:   両立しない前提
options:
  - 「未ログイン」を一時コードで — <何を仕込むか>
  - 「未ログイン」を外す        — test_06 を外す
  - 「ログイン中」を一時コードで — <何を仕込むか>
  - 「ログイン中」を外す        — test_04, test_05 を外す
```

- **残った片方は、ほかの前提と一緒に上の1問ずつに回す。** 一時コードで作る側は、もう聞かない
- **一時コードで作るなら、その項目の分岐を決めているところだけを変える**（ボタンを押したときにログイン中かを見ている分岐を、未ログインの側に固定する、など）。ログイン状態そのものを変えると、もう片方の項目まで同じ状態になり、そちらが撮れなくなる。そこだけで作れない側は、一時コードの選択肢を出さない
- **「わからない、撮ってみる」は、この問いには出さない。** どちらの状態でも、片方は必ず落ちる
- **スクリプトが両立しないと分かるのは、同じ操作の分岐の `when` どうしだけ。** 要素の `when` どうし（「フォローしていないとき」と「フォロー中」）は文言の意味を読まないと分からないので、`rivals` に入らない

**文言から両立しないと読める組が `rivals` の外にあれば、両立しないかを先にユーザーに確かめる。** 自分の読みであって、画面マップに書かれたことではない。上の4択で聞くと、読み違えていても確かなことのように見え、「実は両立する」と返す選択肢も無い。

```
question: 「フォローしていないとき」（test_08）と「フォロー中」（test_09）は、文言から見て同時には成り立たないように読めます（画面マップには書かれていません）。合っていますか？
header:   両立するか
options:
  - 両立しない — 片方をどうするか、続けて聞く
  - 両立する   — どちらもほかの前提と同じく1問ずつ聞く
```

- **「両立しない」なら、上の4択に進む。** 「両立する」なら、ほかの前提と一緒に1問ずつの問いに回す
- **`rivals` の組と同じ呼び出しで聞いてよい。** どちらも返事で次の問いが変わるので、ほかの前提の問いとは別の呼び出しにする
- **question に「画面マップには書かれていません」と添える。** スクリプトの組（マップの分岐から出たもの）と見分けがつくように

### 1. 撮影する

**端末ごとに撮り切ってから次へ移る。** `maestrod.py` が同時に握れるのは1台だけで、切り替えるたびに初回の約10秒を払い直す。

| | 誰が撮るか |
|---|---|
| `flow` を持つ項目 | `run_flows.py`（**メインから1回叩くだけ**） |
| `flow` が無い項目 | `sim-driver`（**`run_flows.py` を走らせ切ってから**呼ぶ。途中に探索を挟まない） |

```bash
python3 <このスキルのディレクトリ>/scripts/run_flows.py <出力先>/manifest.json
```

**叩くと、マニフェストの状態で何をするかが決まる。** 止まっていれば止まったところから、判定が `RETAKE` の項目か、判定の前に撮れなかった項目（`unexpected`）があればそれだけを撮り直し（`flow` の無い項目の `RETAKE` は撮らず、sim-driver に渡す名前を出す）、どちらも無ければ全部を最初から撮る。**1回で全端末を撮る。** 端末はマニフェストに入っているので渡さない。証跡とダンプは `shots/<端末>/`、進捗ログは `progress_<端末>.log`。**Maestro を自分で叩かない** — 経路も `do` の1手ずつも run_flows.py が撮る直前に組み、値もその場で決める。`.work/flows/` の yaml は流したものの記録で、流し直すものではない。落ちたら、そのテストケースの残りの項目だけ飛ばして次のテストケースから続け、最後に「撮れなかった」項目が並ぶ。

分岐に来たら、読んでから進める。

| 来たとき | やること | 読む |
|---|---|---|
| 「撮れなかった」項目がある | **判定に回す前に、retaker に撮り直させる。** その場で探索で撮り直さない（ずれを隠すと次も同じところで落ちる）。retaker でも撮れなかった項目だけ、探索で撮るかこのまま出すかを AskUserQuestion で選んでもらう。**撮れないと返った項目は、残りを撮り直す前に判定まで済ませる**（判定がまだだと、撮り直すたびに一緒に流れる） | `reference/flow-failed.md` |
| 「条件に合う要素が無かった」項目がある | **撮り直さない。そのまま判定に回す。** 探しきって見当たらなかったので、撮り直しても同じ。evidence-judge が `NG` にする（証跡は最後に見た画面）。後ろの巻き添えの項目は `SKIP` | `reference/runtime-inputs.md` |
| 「入力が未定」で終わった | アプリはその画面に居る。ダンプと `expect` から値を決め、同じコマンドに `--value '<値>'` を付けて叩き直す。選ぶ行（`pick`）なら、メッセージに並んだ候補から条件に合う行の ID を `--value` で渡し、無ければ `--next` を付けて叩き直す。**マニフェストは手で書き換えない**（値は `run_flows.py` が `inputs` に書く）。**sim-driver に渡さない** | `reference/runtime-inputs.md` |
| `flow` の無い項目が残った | 端末ごとに sim-driver を呼び、進捗ログに `Monitor` を張る | `reference/explore.md` |
| いまのデータで踏めない項目、すぐ消えるUIがある | 一時コードで再現する。仕込みと revert は自分がやる | `reference/temp-code.md` |

**撮影が全部終わったら、Maestro のデーモンを止める**（`run_flows.py` は止めない。sim-driver は撮影が終わったら自分で止めるが、途中で `TaskStop` すると残る）。XCUITest ドライバが残ると、次の実行で1台に2本繋がり、全操作が `Device became unreachable` で落ちる。

```bash
python3 <このスキルのディレクトリ>/scripts/maestrod.py stop
```

どの項目にも、端末ごとに証跡（`shots/<端末>/<名前>.png`）と同名のダンプ（`.txt`）が並ぶ。判定はその両方を読む。

### 2. 判定は evidence-judge に任せる

証跡を読むのも往復が多い（実測で、メインでやると10項目で39ターン・$4.08、サブに出すと$1.87で判定は一致）。**渡すのはマニフェストのパスと、メインしか知らないことだけ**（下の4つと、実行時に決めた値の理由）。確認項目・期待・証跡・ダンプ・自動確認のIDは全部マニフェストに入っている。

```
~/Desktop/sim-test-report-<日付>-<テーマ>/manifest.json

一時コード: 無し
スコープ外: エラー系（取り直しボタン）。モックサーバーが実データを返す限り踏めない
作成したデータ: 無し
フローが落ちて探索で撮った項目: ipad の test_10, test_13
```

実行時に決めた値（`inputs`）があれば、なぜその値にしたかも添える。条件なしで選ばれた行（`picked`）はマニフェストに入っているので添えなくてよい。`desc` / `result` / `note` / `footer` が埋まって返る。

| `result` | 意味 | 次にやること |
|---|---|---|
| `OK` | 期待どおりだった | — |
| `NG` | **アプリが期待どおり動かなかった** | そのまま報告する。**NG で止まらない** — レポートに載せる事実であって失敗ではない |
| `RETAKE` | **証跡から成否が決められない** | 撮り直す |
| `SKIP` | **撮れなかった**（撮り直しても撮れず、このまま出すとユーザーが決めた） | そのまま報告する。レポートに「撮れなかった」として理由つきで載る |

- **期待のほうが狭かったと思える `NG` も、メインが `OK` に覆さない。** 意図どおりかはプロダクトの判断なので、期待を直すかを AskUserQuestion で選んでもらう → `reference/ng-and-retake.md`
- **`RETAKE` はメインが直さない。** retaker に撮り直させ（`run_flows.py` はマニフェストで `RETAKE` の項目だけを撮り直す）、evidence-judge に撮り直した項目だけ判定し直させる。retaker がマップに足す行を返したら、ユーザーに見せて足してから撮り直す。2周目も残ったら AskUserQuestion で聞く → `reference/ng-and-retake.md`
- 証跡が数枚でレビューの文脈がそのまま効くなら、メインで読んでも構わない（往復が少なければ切り離す意味がない）

#### レポートを出す

`OK` と `NG` と `SKIP` だけになったら生成する。`PENDING` と `RETAKE` が残っていると止まる。**撮れなかった項目をマニフェストから外さない** — `SKIP` にすれば、理由つきのカードと「撮れなかった N」の集計で出る。

```bash
python3 <このスキルのディレクトリ>/scripts/build_report.py <出力先>/manifest.json \
  --title "<テーマ> — 動作確認レポート"
```

**渡すのは題だけ。** 確認環境はマニフェストの `devices` から、実施日は組んだ日から出る。ブランチやコミットは載せない（PR で分かる）。HTMLと同じ場所に1枚PNGも出る。

**項目をまたぐ食い違いは、そのままユーザーに伝える。** footer には入っているが、レポートを開かないと読めない。

### 3. 届ける

SendUserFileでHTML（`display: "render"`）とPNG（`display: "attach"`＝PR貼り付け用）を送り、デスクトップのフォルダパスも伝える。ファイルサイズは気にしない — 画質を落とすより、証跡として読めることを優先する。

あわせて報告する: **撮れなかった項目**（`SKIP`。件数と理由）、**マップに足す候補**（探索で撮った項目、フローが落ちた項目）、NG を期待の訂正で OK にした項目（マップや plan の期待も直す候補）。

## 注意

- テスト実行（xcode-bridge等）はシミュレーターのアプリを再インストールし、ログイン状態を消すことがある。動作確認とテスト実行を同じシミュレーターで行う場合は、先にその影響をユーザーに伝える
- 動作確認でレコード等のデータを作成した場合は、レポートのfooterにその旨を残す（ユーザーが後片付けを判断できるようにする）
