# シミュレーター動作確認レポート

シミュレーターでの動作確認の各ステップを撮影し、HTMLレポート・1枚画像（PNG）・スクリーンショット一式をデスクトップのフォルダ（`~/Desktop/sim-test-report-<テーマのslug>/`）に出力して届ける。HTMLは画像をbase64で埋め込んだ単一ファイル、PNGはそれを1枚に描画したもので、PRコメントにそのまま貼れる。

**レポートに載せる画像はファイルに残るもので撮る**（`xcrun simctl io` か Maestro の `takeScreenshot`）。シミュレーターMCPの screenshot は自分が見るためのもので、ファイルに残らない。

**往復の多い作業はサブエージェントに出す。** 1ターンのコストはその時点のコンテキストの大きさでほぼ決まるので、実装作業で膨らんだ文脈のまま往復すると、中身とほぼ無関係にターン数ぶんのコストが乗る。テストケース作り（`test-case-builder`）、探索での撮影（`sim-driver`）、判定（`evidence-judge`）、撮り直し（`retaker`）がそれにあたる。

**手順の途中で分岐に来たら、指している `reference/*.md` を読んでから進める。** 分岐ごとの書き方（ユーザーに出す2択の形など）はそこにあり、ここには無い。

## 手順

### 0. テストケースを作ってレビューを受ける

シミュレーターを操作する前に、確認項目の一覧をユーザーに提示してレビューを受ける。合意してから実施に入る。

#### 呼ぶ前に決める

`test-case-builder` は文脈を持たないので、次を先に確定させて渡す。

- **何を確認したいか。** PR番号やブランチ（差分から立てる）でも、画面名・機能名（画面マップの `elements` から立てる）でも、観点でもよい。差分が無くても成立する
- **撮る端末とシミュレーター。** `xcrun simctl list devices booted` の一覧から `iphone` / `ipad` それぞれ1台を選び、UDID を控える（渡すときは `iphone=<UDID>` の形）。レイアウトが分岐する変更（サイズクラス、Split View、ポップオーバー）は iPad を入れる価値が高い。**対象が起動していない・同じ機種が複数あって決まらないときはユーザーに確認する。勝手に起動したり、別の端末で代用したりしない** — 全項目が合意と違う端末の証跡になる
- **証跡の出力先**（`~/Desktop/sim-test-report-<テーマのslug>/`）と**対象アプリの bundle id**（`xcrun simctl listapps <UDID>`）
- **対象アプリのリポジトリのパス**。画面マップの有無はサブエージェントが見る（無ければ全項目が探索の plan で返る）

**データに依る値は決めさせない。** 打つ文字は `"runtime": true`、条件で選ぶ行は `"pick": 条件` で plan の `do` に未定のまま残し、撮影のときに埋める。条件が無ければ何も添えず、`run_flows.py` が画面に見えている1件目を押す。事前に決めさせると、サブエージェントがアプリを一通り操作することになる。

**データソース（API、DB、固定データ）も引かせない。** 引いて期待を作ると、モックが間違っていれば期待も一緒に間違う。そのぶん**期待は関係で書く**（「入力欄に出ている語を含む項目だけが並ぶ」）。

#### 返ってきたものを読む

返るのは `<このスキルのディレクトリ>/.work/flows/<slug>/plan.json` と、そこから作った `manifest.json`。**案であって合意ではない**ので、ユーザーに出す前に自分で読む。

- **項目が変更と噛み合っているか。** 外していれば観点を伝えて組み直させる
- **選んだ画面が観点と合っているか。** 画面を取り違えてもフローは通るので、項目の画面idを読むのが唯一の歯止め
- **「候補が絞れなかった項目」は、自分で決めてから出す。** 実装を知っているのは自分
- **「マップに足す候補」は捨てず、**手順3の報告に持っていく
- **トーストのようにすぐ消えるUIは、操作とその撮影が plan の同じ項目に入っているか確かめる** — 別の項目に分かれると、間にツール往復が挟まって撮り逃す
- **直すのは plan.json。** manifest.json もフローも手で直さない — 散文の報告やフローを直しても、次に作り直すと消える。レビューでの1〜2箇所の手直しなら自分で直して下を叩き直し、項目の立て方から見直すときだけ呼び直す（**手順2の `RETAKE` のときは自分で直さない**）

```bash
python3 <このスキルのディレクトリ>/scripts/manifest.py \
  <このスキルのディレクトリ>/.work/flows/<slug>/plan.json <出力先> \
  --device iphone=<UDID> [--device ipad=<UDID>]
```

項目の名前は並び順（`test_01`, …）。フローは端末によらず1組で、証跡だけが `shots/<端末>/<名前>.png` に分かれる。**作業用のファイルはスキル側の `.work/flows/<slug>/` に置き、アプリのリポジトリの下に作らない**（誰も片付けない）。`<slug>` は実行ごとに変える。

- 直す先は2つある。**導線がテストケースに合っていないなら plan の `from` / `do`。マップが実装と違うなら screen-map の仕事**で、フローを手で書き換えて辻褄を合わせない
- **フローが通ることはこの時点では確かめない。** 通らなければ撮影のときに分かる

**経路が組めなかった項目（plan の `explore`）があれば、探索で撮るかマップを作るかをユーザーに2択で選んでもらう。勝手に決めない。** → `reference/unroutable.md` を読んでから書く

#### レビューに出す

**`manifest.json` の `sections` をそのまま読み上げる。組み立て直さない。** 撮る端末を最初に出す。

```
iPhone 17 Pro (iOS 26.5) で撮ります。

**さがす画面**

2. キーワードを打つと入力が止まってから絞り込みが走る
   - 操作: 検索欄に入力する（打つ語は撮るときに決める）
   - 期待: 入力欄に出ている語を、一覧に残っている行がすべて作品名に含む
3. 検索キーで絞り込みが確定する
   - 操作: 検索キーを押す
   - 期待: キーボードが閉じている。一覧は項目2と同じ行のまま
   - ⚠ 画面の自動確認なし。証跡だけで判定

**詳細画面**

6. 一覧の作品をタップすると詳細に移る
   - 操作: アプリを起動し直し、さがす画面で見えている1件目の行をタップする
   - 期待: 詳細画面の作品名が、タップした行の作品名と一致する
9. 書誌と関係者が出る
   - 操作: なし（着いた状態を見る）
   - 期待: 作品名のほかに、書誌の情報と関係者の行が出ている
```

- **撮った画面（`screen`）ごとに、画面マップの `names` の先頭を見出しにする。** 画面 id は出さない。探索の項目（`screen` が空）は `from` の画面の見出しに入れる。どの画面の項目かが読めるのが、画面の取り違えの歯止めになる
- **各項目は `番号. 項目名` のあとに操作・期待・注記を箇条書きで並べる。** 並びを毎回そろえる
- **操作は必ず書く。** 空なら「なし（着いた状態を見る）」とこの文言のまま書く — 省くと、無いのか書き忘れか読めない。`fresh` なら「アプリを起動し直し」、`runtime` は打つ語を撮るときに決める旨、`pick` は条件（「著者が複数いる作品の行」）と撮るときに選ぶ旨、条件の無いパターンの要素なら「見えている1件目」、`see` なら「〜が見えるまでスクロールする」、始める画面が撮る画面と違うなら呼び名で添える。「特定の1件で」のような指摘はここを見て初めて出る
- **期待は必ず書く。** 項目名に含めて省かない
- **前提（`when`）があれば「前提: ログイン中」と書く。** 経路と期待の枝はそれで決まるが、アプリをその状態にはしない。撮るシミュレーターがその状態かをレビューで確かめてもらう
- **`from` までの経路は出さない。** manifest.py が計算するもので、レビューの対象ではない
- **`checked` が空の項目にだけ、その項目の行に「⚠ 画面の自動確認なし」を付ける。探索の項目も `checked` が空なので付ける** — 2択の説明で触れていても、項目の行からは外さない。何も待たずに撮るので、着いたことすら確かめていない。集計や2択で出すと、どの項目の話か読み替えが要る。多ければ確認として弱いことを伝える（`reference/unroutable.md` の末尾）

### 1. 撮影する

**端末ごとに撮り切ってから次へ移る。** `maestrod.py` が同時に握れるのは1台だけで、切り替えるたびに初回の約10秒を払い直す。

| | 誰が撮るか |
|---|---|
| `flow` を持つセクション | `run_flows.py`（**メインから1回叩くだけ**） |
| `flow` が無いセクション | `sim-driver`（**`run_flows.py` を走らせ切ってから**呼ぶ。鎖の途中に探索を挟まない） |

```bash
python3 <このスキルのディレクトリ>/scripts/run_flows.py <出力先>/manifest.json
```

**1回で全端末を撮る。** 端末はマニフェストに入っているので渡さない。証跡とダンプは `shots/<端末>/`、進捗ログは `progress_<端末>.log`。**フローを自分で1本ずつ走らせない** — 導線はフローの中にある。落ちたら次に起動し直す項目（`fresh`）まで飛ばして続け、最後に「撮れなかった」項目が並ぶ。

分岐に来たら、読んでから進める。

| 来たとき | やること | 読む |
|---|---|---|
| 「撮れなかった」項目がある | **その場で探索で撮り直さない。** 探索で撮るかマップを直すかをユーザーに2択で選んでもらう（ずれを隠すと次も同じところで落ちる） | `reference/flow-failed.md` |
| 「入力が未定」で終わった | アプリはその画面に居る。ダンプと `expect`（選ぶ行なら `pick` の条件も）から値を決めて `devices.<端末>.inputs` に書き、同じコマンドを叩き直す。**sim-driver に渡さない** | `reference/runtime-inputs.md` |
| `flow` の無いセクションが残った | 端末ごとに sim-driver を呼び、進捗ログに `Monitor` を張る | `reference/explore.md` |
| いまのデータで踏めない項目、すぐ消えるUIがある | 一時コードで再現する。仕込みと revert は自分がやる | `reference/temp-code.md` |

**撮影が全部終わったら、Maestro のデーモンを止める**（`run_flows.py` も sim-driver も同じデーモンを使い、自分では止めない）。XCUITest ドライバが残ると、次の実行で1台に2本繋がり、全操作が `Device became unreachable` で落ちる。

```bash
python3 <このスキルのディレクトリ>/scripts/maestrod.py stop
```

どの項目にも、端末ごとに証跡（`shots/<端末>/<名前>.png`）と同名のダンプ（`.txt`）が並ぶ。判定はその両方を読む。

### 2. 判定は evidence-judge に任せる

証跡を読むのも往復が多い（実測で、メインでやると10項目で39ターン・$4.08、サブに出すと$1.87で判定は一致）。**渡すのはマニフェストのパスと、メインしか知らないことだけ**（下の4つと、実行時に決めた値の理由）。確認項目・期待・証跡・ダンプ・自動確認のIDは全部マニフェストに入っている。

```
~/Desktop/sim-test-report-<slug>/manifest.json

一時コード: 無し
スコープ外: エラー系（取り直しボタン）。モックサーバーが実データを返す限り踏めない
作成したデータ: 無し
フローが落ちて探索で撮った項目: ipad の test_10, test_13
```

実行時に決めた値（`inputs`）があれば、なぜその値にしたかも添える。条件なしで選ばれた行（`picked`）はマニフェストに入っているので添えなくてよい。`desc` / `result` / `note` / `footer` が埋まって返る。

| `result` | 意味 | 次にやること |
|---|---|---|
| `OK` | 期待どおりだった | — |
| `NG` | **アプリが期待どおり動かなかった** | そのまま報告する。**NG で止まらない** — レポートに載せる事実であって失敗ではない |
| `RETAKE` | **証跡から成否が決められない** | 撮り直す |

- **期待のほうが狭かったと思える `NG` も、メインが `OK` に覆さない。** 意図どおりかはプロダクトの判断なので、期待を直すかをユーザーに2択で選んでもらう → `reference/ng-and-retake.md`
- **`RETAKE` はメインが直さない。** retaker にその項目だけ撮り直させ（`run_flows.py --only`）、evidence-judge にその項目だけ判定し直させる。2周目も残ったらユーザーに聞く → `reference/ng-and-retake.md`
- 証跡が数枚でレビューの文脈がそのまま効くなら、メインで読んでも構わない（往復が少なければ切り離す意味がない）

#### レポートを出す

`OK` と `NG` だけになったら生成する。`PENDING` と `RETAKE` が残っていると止まる。

```bash
python3 <このスキルのディレクトリ>/scripts/build_report.py <出力先>/manifest.json \
  --title "<テーマ> — 動作確認レポート"
```

**渡すのは題だけ。** 確認環境はマニフェストの `devices` から、実施日は組んだ日から出る。ブランチやコミットは載せない（PR で分かる）。HTMLと同じ場所に1枚PNGも出る。

**項目をまたぐ食い違いは、そのままユーザーに伝える。** footer には入っているが、レポートを開かないと読めない。

### 3. 届ける

SendUserFileでHTML（`display: "render"`）とPNG（`display: "attach"`＝PR貼り付け用）を送り、デスクトップのフォルダパスも伝える。ファイルサイズは気にしない — 画質を落とすより、証跡として読めることを優先する。

あわせて報告する: **マップに足す候補**（探索で撮った項目、フローが落ちた項目）、NG を期待の訂正で OK にした項目（マップや plan の期待も直す候補）。

## 注意

- テスト実行（xcode-bridge等）はシミュレーターのアプリを再インストールし、ログイン状態を消すことがある。動作確認とテスト実行を同じシミュレーターで行う場合は、先にその影響をユーザーに伝える
- 動作確認でレコード等のデータを作成した場合は、レポートのfooterにその旨を残す（ユーザーが後片付けを判断できるようにする）
