# 判定に NG・RETAKE が出たら

手順2で evidence-judge が `NG` か `RETAKE` を返したときに読む。

## 期待が狭かったと思える `NG` は2択にする

期待の書き方のほうが狭かった（アプリはそう作られている）と思える `NG` がある。**メインが `OK` に書き換えない。** そう作られているのが意図どおりかは、プロダクトの判断だから。レポートを出す前に、2択にしてユーザーに選んでもらう。

```
test_03  作品名で絞り込むと、残った行の作品名が検索語を含む  [判定: NG]

   「ああ」で絞った5行のうち「あゝ二十年」は、表記に「ああ」を含まない。
   サーバーの絞り込みは読みがな（title_kana）でも一致させている
   （AozoraReaderMockServer/Sources/Database/BooksStorage.swift:33）。

   a) 期待を直して OK にする
      「作品名か読みがなに検索語を含む」に直す。レポートの注記に経緯を残す

   b) NG のままにする
      読みがなで一致するのが意図と違う。アプリか仕様の問題として報告する
```

- **根拠は判定の `desc` と、自分で確かめた実装の場所を並べる。** 仕様を確かめに実装を読むのはよい。決めるのはユーザー
- **a なら、その項目の `expect` を直し、`note` に「期待を訂正: <前> → <後>。<根拠>」と残して `result` を `OK` にする。** 次の回に同じ食い違いが出ないよう、画面マップや plan の期待も直す候補として手順3の報告に挙げる
- **b なら何も書き換えない**

## `RETAKE` は retaker に撮り直させる

**メインが直さない。** 原因を見立て、plan を直し、撮って確かめる往復は、膨らんだ文脈のままやると重い。`retaker` サブエージェントに渡す。

```
evidence-judge    RETAKE ＋ どう直せば撮れるか（その項目の desc）
      ↓
retaker           RETAKE の項目を全部見立て、plan で直せるものは直す。
                  全部 plan で直せたら run_flows.py で撮り直す。
                  マップに足す行が要るものがあれば、叩かずに足す行を返す
      ↓
（マップに足す行があれば）ユーザーに見せて足す → manifest.py → run_flows.py
      ↓
evidence-judge    撮り直した項目だけ判定し直す
```

**渡すのはマニフェストのパスと plan.json のパス。** 撮り直す項目の名前は渡さない — `run_flows.py` はマニフェストで判定が `RETAKE` の項目だけを撮り直す。アプリのリポジトリは plan の `repo` にある。RETAKE の理由はマニフェストのその項目の `desc` に入っている。

- **撮り直すのは `RETAKE` の項目だけ。** `run_flows.py` はそのテストケースの頭で起動し直し、手前の項目を撮らずになぞって、その項目だけ撮る。前のテストケースはなぞらない。ほかの項目の証跡と判定には触らない。手前の項目の値（`inputs`）は前に撮ったときのものを使う。条件なしで見えている1件目を選ぶ行は選び直す（`picked`）
- **`run_flows.py` を叩く前に、`RETAKE` の項目が全部撮り直せる状態かを見る。** 叩くと `RETAKE` の項目は全部撮り直しに行く。マップを足す前の項目、撮れないと返された項目が残っていると、直していないまま撮り直して判定の理由（`desc`）も消える。撮れない項目は先にユーザーに聞き、探索で撮るなら sim-driver に渡してから判定し直してもらう
- **判定し直すのも、撮り直した項目だけ。** evidence-judge に「判定し直す項目: test_07」と渡す。ほかの項目の判定と footer はそのまま残る
- **retaker が返す「マップに足す行」（`ready` / `expect` / `leaves` / `reset`）は、ユーザーに見せてから足す。** 待ちが足りない（着いた画面の読み込み、操作のあとの表示）ものも、前のテストケースが状態を残していたものも、直す先は画面マップ。マップはアプリのリポジトリの `screen-map/screens/<画面>.yaml` にあり、足すとアプリ側の差分になる。足したら `mapctl.py check` を通し、manifest.py を叩き直してから `run_flows.py` で撮り直す。足した行は次の回からも効くので、手順3の報告でもアプリ側の変更として伝える
- **retaker が「撮れない」と返した項目（アプリの外、今のデータでは踏めない）は、ユーザーに聞く。** 探索で撮るか、外して「確認していないこと」に書くか。同じく、「アプリの挙動がおかしい」と返したら NG の候補として伝える
- **2周目も `RETAKE` が残ったら、そこでユーザーに聞く。** 諦めて確認しないまま出すか、別の手を打つかはスコープの判断で、メインが決めることではない
