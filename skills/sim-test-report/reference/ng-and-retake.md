# 判定に NG・RETAKE が出たら

手順2で evidence-judge が `NG` か `RETAKE` を返したときに読む。

## 期待が狭かったと思える `NG` は2択にする

期待の書き方のほうが狭かった（アプリはそう作られている）と思える `NG` がある。**メインが `OK` に書き換えない。** そう作られているのが意図どおりかは、プロダクトの判断だから。レポートを出す前に、AskUserQuestion で選んでもらう（SKILL.md の冒頭「ユーザーに選んでもらうときは AskUserQuestion で聞く」）。根拠は長いので、本文に書いてから聞く。

```
本文:
  test_03（作品名で絞り込むと、残った行の作品名が検索語を含む）は NG でした。
  「ああ」で絞った5行のうち「あゝ二十年」は、表記に「ああ」を含まない。
  サーバーの絞り込みは読みがな（title_kana）でも一致させている
  （AozoraReaderMockServer/Sources/Database/BooksStorage.swift:33）。

question: test_03 の期待を直しますか？
header:   test_03の期待
options:
  - 期待を直して OK にする — 「作品名か読みがなに検索語を含む」に直す。レポートの注記に経緯を残す
  - NG のままにする       — 読みがなで一致するのが意図と違う。アプリか仕様の問題として報告する
```

- **根拠は判定の `desc` と、自分で確かめた実装の場所を並べる。** 仕様を確かめに実装を読むのはよい。決めるのはユーザー
- **NG ごとに1問。** 期待が狭い理由は項目ごとに違うので、まとめない
- **期待を直すなら、その項目の `expect` を直し、`note` に「期待を訂正: <前> → <後>。<根拠>」と残して `result` を `OK` にする。** 次の回に同じ食い違いが出ないよう、画面マップや plan の期待も直す候補として手順3の報告に挙げる
- **NG のままなら何も書き換えない**

## `RETAKE` は retaker に撮り直させる

**メインが直さない。** 原因を見立て、plan を直し、撮って確かめる往復は、膨らんだ文脈のままやると重い。`retaker` サブエージェントに渡す。

```
evidence-judge    RETAKE ＋ どう直せば撮れるか（その項目の desc）
      ↓
retaker           RETAKE の項目を全部見立て、plan で直せるものは直す。
                  全部 plan で直せたら run_flows.py で撮り直す。
                  マップに足す行が要るものがあれば、叩かずに足す行を返す
      ↓
（マップに足す行があれば）ユーザーに見せて足す → manifest.py → run_flows.py
      ↓
evidence-judge    撮り直したテストケースの項目だけ判定し直す
```

**渡すのはマニフェストのパスと plan.json のパス。** 撮り直す項目の名前は渡さない — `run_flows.py` はマニフェストで判定が `RETAKE` の項目のあるテストケースだけを撮り直す。アプリのリポジトリは plan の `repo` にある。RETAKE の理由はマニフェストのその項目の `desc` に入っている。

- **撮り直すのは `RETAKE` の項目のあるテストケースだけ。** `run_flows.py` はそのテストケースの頭で起動し直し、手前と後ろの項目も含めて全部撮る。テストケースの中の項目は前後で当てにし合うので、`RETAKE` の項目だけを新しく撮ると、データが変わるアプリ（API の中身が変わる、ランダムに並ぶ）では前提と証跡が食い違う。ほかのテストケースの証跡と判定には触らない
- **撮り直すテストケースの実行時の値（`inputs`）は決め直す。** `run_flows.py` が撮り直しを始めるときに空にするので、打つ文字や条件つきで選ぶ行で止まる。前の回と同じ値でよければ同じ値を `--value` で渡す（`reference/runtime-inputs.md`）。条件なしで見えている1件目を選ぶ行は、いつもどおり選び直す（`picked`）
- **撮り直すテストケースに、判定を付けて外した項目（`SKIP` にした、探索で撮った）があれば、その端末では流さない。** `run_flows.py` がその端末の `unexpected` に `settled` の印を付け、証跡と判定に触らない。後ろの項目は前提が無いので、巻き添え（`unexpected` の `skipped`）になる。ほかの端末では撮るので判定は `PENDING` に戻る — 判定し直すとき、探索で撮った項目なら「フローが落ちて探索で撮った項目」としてもう一度渡す
- **`run_flows.py` を叩く前に、`RETAKE` の項目が全部撮り直せる状態かを見る。** 叩くと `RETAKE` の項目は全部撮り直しに行く。マップを足す前の項目、撮れないと返された項目が残っていると、直していないまま撮り直して判定の理由（`desc`）も消える。撮れない項目は先にユーザーに聞き、探索で撮るなら sim-driver に渡してから判定し直してもらう。撮らないなら判定し直す項目として「撮り直しを諦めた項目」で渡し、`SKIP` にしてもらう（`RETAKE` のままだと撮り直しに行く）
- **判定し直すのも、撮り直したテストケースの項目だけ。** `run_flows.py` が最後に「判定し直す項目: test_06, test_07, test_08」と出すので、それを evidence-judge に「判定し直す項目」として渡す。手前の項目も新しい証跡になっているので、前の回に `OK` だった項目も判定し直す（前の回の判定とずれたら、新しい証跡の判定が正）。ほかの項目の判定と footer はそのまま残る
- **retaker が返す「マップに足す行」（`ready` / `expect` / `leaves` / `reset`）は、ユーザーに見せてから足す。** 待ちが足りない（着いた画面の読み込み、操作のあとの表示）ものも、前のテストケースが状態を残していたものも、直す先は画面マップ。マップはアプリのリポジトリの `screen-map/screens/<画面>.yaml` にあり、足すとアプリ側の差分になる。足したら `mapctl.py check` を通し、manifest.py を叩き直してから `run_flows.py` で撮り直す。足した行は次の回からも効くので、手順3の報告でもアプリ側の変更として伝える
- **retaker が「撮れない」と返した項目（アプリの外、今のデータでは踏めない）は、AskUserQuestion で聞く。** 探索で撮るか、撮らずに撮れなかった項目としてレポートに載せる（`SKIP`）か。マニフェストから外して「確認していないこと」に書かない — 項目の話が footer に回り、レポートの「全 N 項目」からも消える。同じく、「アプリの挙動がおかしい」と返したら NG の候補として伝える
- **2周目も `RETAKE` が残ったら、そこで AskUserQuestion で聞く。** 諦めて確認しないまま出すか、別の手を打つかはスコープの判断で、メインが決めることではない。別の手（一時コードで作る、探索で撮る、など）は、打てるものを選択肢に並べる。諦めるなら、上と同じく「撮り直しを諦めた項目」として判定に渡し、`SKIP` にしてもらう
