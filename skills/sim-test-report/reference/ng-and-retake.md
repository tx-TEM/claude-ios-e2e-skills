# 判定に NG・RETAKE が出たら

手順2で evidence-judge が `NG` か `RETAKE` を返したときに読む。

## 期待が狭かったと思える `NG` は2択にする

期待の書き方のほうが狭かった（アプリはそう作られている）と思える `NG` がある。**メインが `OK` に書き換えない。** そう作られているのが意図どおりかは、プロダクトの判断だから。レポートを出す前に、2択にしてユーザーに選んでもらう。

```
test_03  作品名で絞り込むと、残った行の作品名が検索語を含む  [判定: NG]

   「ああ」で絞った5行のうち「あゝ二十年」は、表記に「ああ」を含まない。
   サーバーの絞り込みは読みがな（title_kana）でも一致させている
   （AozoraReaderMockServer/Sources/Database/BooksStorage.swift:33）。

   a) 期待を直して OK にする
      「作品名か読みがなに検索語を含む」に直す。レポートの注記に経緯を残す

   b) NG のままにする
      読みがなで一致するのが意図と違う。アプリか仕様の問題として報告する
```

- **根拠は判定の `desc` と、自分で確かめた実装の場所を並べる。** 仕様を確かめに実装を読むのはよい。決めるのはユーザー
- **a なら、そのセクションの `expect` を直し、`note` に「期待を訂正: <前> → <後>。<根拠>」と残して `result` を `OK` にする。** 次の回に同じ食い違いが出ないよう、画面マップや plan の期待も直す候補として手順3の報告に挙げる
- **b なら何も書き換えない**

## `RETAKE` は test-case-builder に組み直させる

**メインが直さない。** plan.json もフローも触らない（手順0の「1〜2箇所なら自分で直す」はレビューのときの話で、ここには当てはまらない）。フローを組み直すのはテストケース側の作業で、`test-case-builder` の仕事。実測で、メインがこれをやったとき31ターン・$2.98かかった（膨らんだ文脈のまま経路を組み直していた）。

```
evidence-judge    RETAKE ＋ どう直せば撮れるか
      ↓
test-case-builder plan を直して manifest.py を叩き直す（フローも全部書き直される）
      ↓
run_flows.py      撮り直す。撮った項目の判定は捨てられる
      ↓
evidence-judge    判定し直す
```

- **1項目だけ撮り直すことはしない。** フローは鎖なので、1本直すと同じ鎖の下流が別の前提で動く。**全部組み直して全部撮る。** 撮影は10項目で70秒なので、区間を切り分ける手間のほうが高い
- **2周目も `RETAKE` が残ったら、そこでユーザーに聞く。** 諦めて確認しないまま出すか、別の手を打つかはスコープの判断で、メインが決めることではない
