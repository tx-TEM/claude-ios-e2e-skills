# 入力が未定で終わったら値を決める

手順1で `run_flows.py` が「入力が未定」で実行を終えたときに読む。

```
iphone test_02 入力が未定（BROWSE_SEARCH_FIELD）。
いまこの画面に居る。見て 打つ文字を BROWSE_SEARCH_FIELD に決め、devices.iphone.inputs に書き、同じコマンドをもう一度叩けば続きから走る。
iphone のここから先の 6件はまだ撮っていない。
```

止まるのは2つ。plan で `"runtime": true` を付けた**打つ文字**と、`"pick": 条件` を付けた**パターンの要素のどれを押すか**。後者はメッセージに条件が出る（`見て 条件「著者が複数いる作品」に合う browse.book_row.* を選んで BROWSE_BOOK_ROW に決め、…`）。**条件の無いパターンの要素ではここに来ない** — `run_flows.py` が画面に見えている1件目を選び、`devices.<端末>.picked` に書いて先へ進む。

**値を使う操作の手前で、項目のフローが割れている**（セクションの `parts`）。前の本が目的の画面まで運び、対象が見えるまでスクロールして止まる。先へ走らせると画面が変わり、値を決めるために見ることができなくなるので、そこで終えている。**終えた時点で、アプリはその画面に居る。**

```bash
python3 <このスキルのディレクトリ>/scripts/maestrod.py inspect <UDID> peek
```

**そのセクションの `title` / `expect`（選ぶ行なら `pick` の条件も）と、ダンプの中身から値を決める。** 片方だけでは決まらない — テストケースが「何を確かめたいか」を、ダンプが「いまどんなデータが入っているか」を持っている。

```
expect: 入力した語を含む項目だけが並ぶ        →  複数の行に共通する部分（牛乳）
expect: 1件に絞れる                          →  1行にしか出ない語
pick:   著者が複数いる作品                    →  その条件を満たしている行の、ID の * に当たる部分
```

**ダンプに出ている文字列をそのまま使うとは限らない。** 上の1つ目は `牛乳, 1,000ml` と `低脂肪牛乳, 900ml` から `牛乳` を取り出している。選ぶ行は、ダンプの id の欄（`browse.book_row.低脂肪牛乳`）のうち、パターンの `*` に当たる部分（`低脂肪牛乳`）を書く。**同じ名前の行が複数あるときは `低脂肪牛乳#2` のように書く** — 画面に見えている同じ名前の行のうち、上から2件目。何も付けなければ見えているうちの1件目。`run_flows.py` が走らせる直前に画面を読み、同じ ID の行の何番目か（Maestro の `index`）を数えて押す。書いた行が画面に見えていなければ、その項目は撮れずに次の鎖へ進む。決めたら、そのセクションの `devices.<端末>.inputs` に書く。**値は端末ごと** — その端末の画面を見て決める。**決めた値は、正規表現のエスケープをかけずに書く。** 押す行のようにセレクタ（正規表現）に入る値は、`run_flows.py` がマニフェストの `input_use` を見てエスケープする。自分でもかけると二重になって当たらない。

```json
"devices": { "iphone": { "inputs": { "BROWSE_SEARCH_FIELD": "牛乳" } } }
```

**同じコマンドをもう一度叩く。** 止まった地点（項目と、その何本目か）はマニフェストの `resume` に記録されているので、撮り終えた端末は飛ばし、止まった端末の止まった本から走る。**手前は撮り直さない。**

- **未定の値の数だけ繰り返す。** 1回に1つずつ終える。1つの項目で2回以上止まることもある（打つ文字を決めてから、絞られた一覧で行を選ぶなど）
- **決めた値は手順2で使う。** 判定する側は「何を打ったか・なぜその行か」を知らないと期待と突き合わせられない（ダンプの入力欄にも出るが、なぜその値かは出ない）
- **sim-driver には渡さない。** 渡すと、その鎖の残りが全部モデルの仕事になる
