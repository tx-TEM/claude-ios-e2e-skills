# 経路が組めなかった項目を2択にする

手順0のレビューで、plan の `explore` に入った項目（manifest.py が経路を組めなかった項目）があるときに読む。

**組めないことは、シミュレーターを触る前に分かっている。** だから「探索で撮ります」と勝手に決めずに、レビューで選択肢として出す。

```
4. 履歴から項目を開き直せる  [history]

   ⚠ history 画面のマップがありません。2つの進め方があります。

   a) このまま探索で撮る
      すぐ撮れる。ただし導線は実行時に探すので、この項目だけ
      「その画面に着いた」という画面の自動確認が付かず、判定は証跡だけが根拠になる

   b) 先に history 画面のマップを作る
      screen-map スキルで、アプリのソースに accessibilityIdentifier を振る
      （＝アプリ側の変更。別ブランチ・別PRになる）。実測での検証も要るので
      時間がかかるが、この画面は以降ずっとフローで撮れる
```

- **2択は対等ではない。** b はアプリのソースを編集する。**時間だけでなく、別PRが増えることを明示する**
- 理由は manifest.py が返した文言をそのまま使う（「画面 settings がマップに無い」「`in_tree: false`（座標が要る）」）。**言い換えない** — 言い換えると、マップのどこを直せばよいかが読めなくなる
- **どの項目がその画面に依存しているかを並べる。** 1画面のマップが無いせいで3項目が探索になるなら、b を選ぶ価値が変わる
- **2択はレビューの項目一覧とは別に出す。** 一覧のほうの項目の行にも「⚠ 画面の自動確認なし」を付ける（探索の項目は `checked` が空）。2択に書いたから一覧では省く、としない
- a を選ばれた項目は、plan の `explore` にそのまま残る。手順3の報告で「マップに足す候補」として改めて挙げる。**そのときに断ればよく、いま決め打ちする理由はない**

## 自動確認なしが多いとき

`checked` が空の項目が多ければ、**確認として弱い**ことを正直に伝える。マップのアクションに `expect` を足せばそのまま付くので、ここも同じ形の2択にできる（このまま撮る / 先に `expect` を足す）。

- **アプリの外に出る操作（`expect` が `external`）で終わる項目は、この2択に入れない。** フローは外を確かめない（外に居るまま撮る）ので、`expect` を足しても付かない。「⚠ 画面の自動確認なし」は同じく付ける
