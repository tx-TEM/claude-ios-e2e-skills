# 経路が組めなかったテストケースを2択にする

手順0のレビューで、plan で `explore` の付いたテストケース（manifest.py が経路を組めなかった項目を含むもの）があるときに読む。

**組めないことは、シミュレーターを触る前に分かっている。** だから「探索で撮ります」と勝手に決めずに、レビューで AskUserQuestion で聞く（SKILL.md の冒頭「ユーザーに選んでもらうときは AskUserQuestion で聞く」）。

```
question: test_04〜test_06（履歴から項目を開き直せる）は、経路が組めません（画面 history がマップに無い）。どう進めますか？
header:   history
options:
  - 探索で撮る         — すぐ撮れる。ただし導線は実行時に探すので、この3項目は「その画面に着いた」
                         という画面の自動確認が付かず、判定は証跡だけが根拠になる
  - 先にマップを作る   — screen-map スキルで、アプリのソースに accessibilityIdentifier を振る
                         （アプリ側の変更。別ブランチ・別PRになる）。実測での検証も要るので時間が
                         かかるが、この画面は以降ずっとフローで撮れる
```

- **2択は対等ではない。** マップを作る側はアプリのソースを編集する。**時間だけでなく、別PRが増えることを description に明示する**
- **組めない理由ごとに1問。** 同じ画面のせいで組めないテストケースはまとめる
- 理由は manifest.py が返した文言をそのまま使う（「画面 settings がマップに無い」「`in_tree: false`（座標が要る）」）。**言い換えない** — 言い換えると、マップのどこを直せばよいかが読めなくなる
- **どの項目がその画面に依存しているかを並べる。** 1画面のマップが無いせいで3項目が探索になるなら、マップを作るほうを選ぶ価値が変わる。**組めないのが1項目でも、テストケースごと探索になる**ので、同じテストケースのほかの項目も並べる
- **2択はレビューの項目一覧とは別に聞く。** 一覧のほうの項目の行にも「⚠ 画面の自動確認なし」を付ける（探索の項目は `checked` が空）。問いに書いたから一覧では省く、としない
- 探索で撮ると選ばれたテストケースは、plan の `explore` が付いたまま残る。手順3の報告で「マップに足す候補」として改めて挙げる。**そのときに断ればよく、いま決め打ちする理由はない**

## 自動確認なしが多いとき

`checked` が空の項目が多ければ、**確認として弱い**ことを正直に伝える。マップのアクションに `expect` を足せばそのまま付くので、ここも同じ形で AskUserQuestion で聞ける（このまま撮る / 先に `expect` を足す。足す側はアプリ側の変更になることを description に書く）。

- **アプリの外に出る操作（`expect` が `external`）で終わる項目は、この2択に入れない。** フローは外を確かめない（外に居るまま撮る）ので、`expect` を足しても付かない。「⚠ 画面の自動確認なし」は同じく付ける
