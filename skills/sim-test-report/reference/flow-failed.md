# フローが落ちた項目を2択にする

手順1で `run_flows.py` の最後に「撮れなかった」項目が並んだときに読む。

**落ちたのは、フローが待っていた画面や要素が出なかったから。** マップが実装やその端末の見え方とずれている（OS によって ID が無い、など）ことが多い。**その場で探索で撮り直して先へ進めない** — ずれを隠すと、次の回も同じところで落ちる。経路が組めなかった項目と同じく、選択肢として出す。

```
test_10, test_13  戻るボタンで前の画面に戻る  [iPad]

   ⚠ フローが落ちました: ^BackButton$ が10秒で出ない（iPad Pro 11-inch (M4) / iOS 18.3）。
   落ちた地点の画面では、戻るボタンにラベル「Back」だけがあり ID がありません。
   iPhone（iOS 26.5）では通っています。

   a) この項目だけ探索で撮る
      すぐ撮れる。ただしこの項目には画面の自動確認が付かず、判定は証跡だけが根拠になる

   b) 先に画面マップを直す
      screen-map スキルで、戻るボタンに ID を振るかラベルでも叩けるようにする
      （＝アプリ側の変更。別ブランチ・別PRになる）。直せば以降ずっとフローで撮れる
```

- **理由は落ちたフローの行と、落ちた地点の画面から書く。** 何を待って何が出なかったか。**言い換えない**
- **どの端末で落ちたかを書く。** ほかの端末で通っていれば、それも書く — OS や画面サイズによるずれの手がかりになる
- **巻き添えで撮れていない項目も並べる。** 落ちた項目のあと、同じ鎖（次の `fresh` まで）の項目は走っていない
- **アプリの不具合と読めるなら、2択の前にそう伝える。** 落ちた地点の画面が期待と違う状態（遷移しない、エラーが出ている）なら、それはマップのずれではなく `NG` の候補
- **a を選ばれた項目は sim-driver に渡す**（`flow` があるセクションでも、その名前を渡す。渡し方は `reference/explore.md`）。判定に渡すときも「フローが落ちて探索で撮った項目」として伝える。手順3の報告で「マップに足す候補」として改めて挙げる
- **b を選ばれたら、マップを直してから `manifest.py` と `run_flows.py` を叩き直す**
