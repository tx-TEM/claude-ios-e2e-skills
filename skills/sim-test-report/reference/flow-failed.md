# フローで撮れなかった項目を撮り直す

手順1で `run_flows.py` の最後に「撮れなかった」項目が並んだときに読む。

**撮れなかったのは撮る側の問題なので、判定に回す前に撮り直す。** 落ちたのは、フローが待っていた画面や要素が出なかったから。待ちが足りない、マップが実装やその端末の見え方とずれている（OS によって ID が無い、など）、前提の状態が無い、のどれかが多い。

```
run_flows.py        撮れなかった項目に unexpected を付ける
      ↓
retaker             原因を見立てる。plan で直せるものは直して run_flows.py で撮り直す
                    マップに足す行が要るもの・撮れないものがあれば、叩かずに返す
      ↓
（撮れないと返った項目があれば）先に AskUserQuestion で聞いて片付ける：
                    探索で撮る → sim-driver → evidence-judge（その項目だけ）
                    このまま出す → evidence-judge（その項目だけ SKIP）
      ↓
（足す行があれば）ユーザーに見せて足す → mapctl.py check → manifest.py → run_flows.py
      ↓
まだ撮れない項目だけ、AskUserQuestion で聞く：探索で撮る / このまま出す
      ↓
evidence-judge      判定。このまま出す項目は SKIP（撮れなかった）と理由
```

**撮り直す項目はマニフェストの印で決まる。** `run_flows.py` も retaker も、判定がまだ（`PENDING`）で `unexpected` の付いた項目を全部撮り直しに行く（名前では選べない）。撮れないと分かった項目（前提の状態が無い、フローでは撮れない）を外す手は、**先に判定を付けることだけ**。付けずに残すと、ほかの項目を撮り直すたびに一緒に流れ、そのたびに起動し直して落ちる。

## 1. retaker に撮り直させる

**メインが直さない。その場で探索で撮り直して先へ進めない。** 原因を見立てずに探索で撮ると、マップのずれが隠れて次の回も同じところで落ちる。渡し方は `RETAKE` と同じ（`reference/ng-and-retake.md`）で、マニフェストのパスと plan.json のパスだけ。撮り直す項目は、判定がまだで `unexpected` の付いた項目としてマニフェストから決まる（`run_flows.py` も同じ項目を撮り直す）。

- **retaker がマップに足す行を返したら、ユーザーに見せてから足す。** 戻るボタンに ID が無い、`ready` が足りない、など。マップはアプリのリポジトリにあり、足すとアプリ側の差分（別ブランチ・別PR）になる。足したら `mapctl.py check` を通し、`manifest.py` と `run_flows.py` を叩き直す。`unexpected` はマニフェストを作り直しても残るので、撮れなかった項目のあるテストケースだけを撮り直す。足した行は手順3の報告でもアプリ側の変更として伝える
- **retaker が「アプリの挙動がおかしい」と返したら、`NG` の候補としてユーザーに伝える。** 落ちた地点の画面が期待と違う状態（遷移しない、エラーが出ている）なら、マップのずれではない。探索で撮れば、その画面を証跡にして判定に `NG` を付けさせられる
- **retaker が前提の状態が無いと返したら**（ログインしていない、データが無い、初回だけの表示がもう済んでいる）、それをユーザーに伝える。前提はレビューで聞いてある（SKILL.md の「前提を聞く」）ので、ここに来るのは「その状態にしてある」と返ったのに状態が違っていたとき、「わからない、撮ってみる」で撮って状態が無かったとき、`when` に書かれていない状態が要ったとき。前提を作れば撮れるなら `reference/temp-code.md` の一時コードで作る案を添えて、下の2択に回す
- **retaker が撮れないと返した項目（前提の状態が無い、フローでは撮れない、アプリの挙動がおかしい）は、残りを撮り直す前に片付ける。** 下の2択をその場で聞き、答えに合わせて判定まで済ませてから、残りの項目に進む（足す行を足す、retaker に渡し直す、`run_flows.py` を叩く）。判定がまだのまま残すと、残りを撮り直すたびに一緒に流れる。2回目まで待たない — 撮れないと返った項目は、何回流しても撮れない
- **retaker に渡す前に、撮れないと分かっている項目が残っていないかを見る。** 前の回で「このまま出す」と決めたのに判定に渡していない項目、前提を聞いて状態が無いと分かった項目など。あれば上と同じく先に判定まで済ませてから渡す
- **retaker に渡すのは2回まで。** 2回で撮れなければ、見立てが外れている可能性が高い。下の2択に回す

## 2. まだ撮れない項目は2択にする

retaker でも撮れなかった項目（撮れないと返された、2回で撮れなかった）だけを、AskUserQuestion で聞く（SKILL.md の冒頭「ユーザーに選んでもらうときは AskUserQuestion で聞く」）。理由は長いので、本文に書いてから聞く。

```
本文:
  test_10, test_13（戻るボタンで前の画面に戻る）の iPad が、フローで撮れませんでした。
  ^BackButton$ が10秒で出ない（iPad Pro 11-inch (M4) / iOS 18.3）。落ちた地点の画面では、
  戻るボタンにラベル「Back」だけがあり ID がありません。iPhone（iOS 26.5）では通っています。
  マップに足す行（戻るボタンをラベルで叩く）は見送りました。

question: test_10, test_13 の iPad をどうしますか？
header:   test_10の撮影
options:
  - 探索で撮る   — すぐ撮れる。ただしこの項目には画面の自動確認が付かず、判定は証跡だけが根拠になる
  - このまま出す — この項目の iPad は確かめないまま出す。レポートには理由つきで「撮れなかった」と出る
```

- **落ちた理由が違う項目は、別の問いにする。** 同じ原因で落ちた項目（と、その巻き添えの項目）は1問にまとめる
- **理由は落ちたフローの行と、落ちた地点の画面から書く。** 何を待って何が出なかったか。**言い換えない**
- **どの端末で落ちたかを書く。** ほかの端末で通っていれば、それも書く — OS や画面サイズによるずれの手がかりになる
- **retaker が何を試したかを書く。** マップに足す行を見送った、plan を直して撮り直したがまた落ちた、など
- **並べる項目はマニフェストの `devices.<端末>.unexpected` から拾う。** `failed` が落ちた項目（`reason` に何が起きたか）、`skipped` が巻き添えで走らせていない項目（同じテストケースの後ろの項目）。巻き添えの項目も並べる
- **探索で撮ると選ばれた項目は sim-driver に渡す**（`flow` がある項目でも、その名前を渡す。渡し方は `reference/explore.md`）。落ちた項目がテストケースの途中なら、手前の項目も一緒に渡す — 手前の項目の操作をなぞらないと、その項目の前提の状態にならない。判定に渡すときも「フローが落ちて探索で撮った項目」として伝える。手順3の報告で「マップに足す候補」として改めて挙げる
- **このまま出すと選ばれたら、`unexpected` を残したまま evidence-judge に渡す。** evidence-judge が `SKIP`（撮れなかった）と理由を書く。**マニフェストから外さない** — 外すと、項目の話が footer に回り、レポートの「全 N 項目」からも消える。**判定の前に `run_flows.py` を叩かない** — 撮れなかった項目をまた撮り直しに行く（判定が `SKIP` を付けたあとは拾わない）
- **ほかにまだ撮り直す項目があるうちに判定に渡すときは、その項目だけを判定させる。** evidence-judge に「判定し直す項目」と「撮り直しを諦めた項目」（理由つき。retaker が返した原因）の両方でその名前を渡す。判定し直す項目を渡さないと、撮り直す途中の項目まで `SKIP` になる。**判定を付けた項目が、まだ撮り直す項目と同じテストケースにあると、撮り直しでほかの端末の証跡が撮り直され、判定が `PENDING` に戻る**（判定を付けた端末では流さない。`reference/ng-and-retake.md`）。撮り直しのあと、`run_flows.py` が出す「判定し直す項目」に並ぶので、探索で撮った項目なら「フローが落ちて探索で撮った項目」としてもう一度渡す。探索で撮った項目も同じく、その項目だけ判定させる。全体の判定は、撮り直しが終わってから手順2でする
