# 経路になる

マップは要素の操作の `expect: {screen, via}` で辺を持っているので、起点からの経路はグラフの最短路として機械的に組める。このスキルの `scripts/route.py` がそれをやる。sim-test-report はフローを作るときに同じ経路の計算（`scripts/screenmap/route.py`）を使って、テストケースの項目と項目の間を繋ぐ。**このスキルの成果物がそのまま sim-test-report の入力になるのは、ここを通してのこと。**

```bash
R=~/.claude/skills/screen-map/scripts/route.py

python3 $R screens --repo <アプリ>           # 画面の一覧（呼び名・できること）
python3 $R which <パス...> --repo <アプリ>   # 変更したファイルから対象画面を引く
python3 $R path <画面id>... --repo <アプリ>  # そこまでの経路を人が読む形で出す
python3 $R check --repo <アプリ>             # 自己テスト（到達可否・不整合・切れている箇所・書き足すもの・鮮度）
python3 $R path <画面id> --when ログイン中 --repo <アプリ>   # 条件つきの辺を通す前提を渡す
```

確認項目ごとのフローは sim-test-report の `manifest.py` が書く（中で route.py の経路計算を使う）。項目は経路を持たず、前の項目が終わった画面から項目の起点までは、マップから計算して繋ぐ。

書く側として効いてくるのは次の点。

- **`anchor` と `ready` が到達判定になる。** 着くたびに、anchor → `ready` → アニメーションの落ち着き待ち（上限3秒）の順に待ってから次に進む。`anchor` が無い画面は経路に使えても「着いた」を確かめられない。`ready` が無い画面は、読み込み中のまま次の操作や撮影に進むことがある
- **辺になるのは、`expect` に `screen` と `via: push` / `modal` / `tab` を持つ操作だけ。** 先の画面はファイルとして実在する必要がある。無ければ `check` が不整合として出す。`stub` を置くのはこのため
- **同じ長さなら `via: tab` を多く通る経路を採る。** タブバーはいつも同じ位置にあり、画面の下の方のカードを押すより確実。タブの切り替えを `push` と書くと、この選び分けが効かない
- **条件つきの要素（`when`）と、`when` で分かれる `expect` の枝は、確認項目の前提（plan の `when`）に同じ文言があるときだけ経路に使う。** 意味は読まず、文字列が一致するかだけを見る。前提なしで通ると着く先が読めないので、そこで止まって「条件つき」と返す。条件の無い入口がほかにもあるなら、それも書いておく（前提なしで通れる経路になる）
- **`screen: back`（`via: back` / `dismiss`）は経路計算の復路になる。** 往路の探索からは外れるが、**深く入った先から戻る経路はこれで組む**。戻る操作を持たない画面は、そこから先へ進むしかなくなる（`route.py` が「戻る操作がマップに無いので向かえない」と返す）ので、push で入る画面には戻る操作を書く
- **戻る操作の戻り先は、`route.py` が歩いた履歴から出す。** どこから来たかで変わるので、マップには書かない
- **押す前・見る前に、スクリプトが必ず `scrollUntilVisible` を入れる。** 画面外の要素にもそのまま届くので、マップにスクロールの操作を書かない。`gestures` の `scroll: down` / `up` は、スクロールすること自体に結果がある操作（ページ送り）のためのもの
- **パターンの要素（ID の末尾 `*`）のどれを押すかは、スクリプトが実行時に決める。** 条件が無ければ `run_flows.py` が画面に見えている1件目をダンプから選び、条件があれば plan の `do` の `pick` に書いた条件で選ばせる。どちらもその手前でフローを割り、対象が見えるまでスクロールして止まってから決める。選んだ値はマニフェストに残るので、**証跡を読んで判定するのは呼び出し元の仕事**で、マップ側に「突き合わせるために読む要素」のIDを足す必要はない。ID を具体的に書けば（`tap:item_list.cell.牛乳`）決め打ちで当たる
- **`auto_shows` は着くたびに確かめる。** 並べた画面に push / modal / tab で入ると、その画面の anchor を待つ**前に**「自動表示の画面の anchor が出ていたら、その `screen: back` の操作を叩く」が積まれる。`after` つきの項目は、逆に `after` の画面から戻ったときだけ積まれる。自動表示が出ている間は、下の画面の anchor がツリーから隠れるので、この順番でないと落ちる。出ていないときに1つ約7秒かかるので、実際に出る画面にだけ並べ、`after` で絞れるものは絞る。自動表示の画面は遷移で入らないが、出る先に着けるなら `check` は到達できるものとして数え、項目の `from` にも書ける（出る先まで行って、閉じずに待つ。`after` つきなら after の画面へ行って戻ってから待つ）
- **`in_tree: false` の要素はそこで経路が切れる。** その先の画面は到達不能として `check` に出る
- **`text` の値はマップが持たない。** 呼ぶ側が plan の `do` に `"input"` か `"runtime": true` を添えて渡す。何を打つかを決めるのはテストケース
- **`expect` の無い操作は、何も確かめない。** 遷移しない操作では、その証跡は画像だけが根拠になる。`route.py path` はそれを明示して出す
- **アクションの `summary` はフローのコメントになる。** 組んだフローはそのままレビューに出るので、`summary` が「何が起きるか」を書けていないと、人が導線を確かめられない
- **`expect` や `ready` が指す ID は、どこかの画面の要素として定義する。** 定義されていなければ `check` が不整合として出す。観測点も見るだけの要素として `elements` に並べる

**経路が組めないことは、マップの穴がそのまま出たもの。** `route.py` は推測して繋がない。埋めるのはこのスキルの仕事で、次にこのアプリを触るときの対象リストになる。
