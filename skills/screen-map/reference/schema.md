# スキーマ

手順4で `screens/*.yaml` を書くときに読む。

**マップが持つのは「画面に何があり、操作するとどうなるか」という事実だけ。** スクロール、待ち、どの行を押すかといった実行時の判断はスクリプト（sim-test-report の route.py / run_flows.py）が持つ。マップに書かない。

```yaml
# config.yaml
start: root                # 起動直後の画面
```

```yaml
# screens/item_list.yaml — ファイル名が画面id（item_list）
anchor: item_list          # この画面にいることを証明するID。画面idそのもの

names: [アイテム一覧, 一覧画面, 記録一覧]   # この画面の呼び名。社内での通称も入れる

summary: アイテムの一覧。お気に入りの登録、詳細への遷移ができる   # 何の画面で何ができるか1行

files:                     # 主要ファイル（VC / VM / View）＋IDを振ったファイル
  - Features/Item/ItemListViewController.swift
  - Features/Item/ItemListViewModel.swift
  - Features/Item/ItemCell.swift

# 読み込み完了の目印。any はどれか1つ、all は全部
ready:
  any: [item_list.cell.*, item_list.empty_view]

elements:
  - id: item_list.menu_button
    name: メニューボタン（左上）
    actions:
      - tap:
        summary: 設定を開く
        expect: {screen: settings, via: modal}

  # ID の末尾が * の要素は、同じ種類の要素が複数並ぶ。どれを押すかはスクリプトが実行時に決める
  - id: item_list.cell.*
    name: アイテムの行（ID は表示中の名前）
    actions:
      - tap:
        summary: アイテムの詳細を開く
        expect: {screen: item_detail, via: push}

  - id: item_list.search_field
    name: 検索欄（上部）
    actions:
      - text:
        summary: 入力が止まると絞り込みを送り、一覧が入れ替わる
        expect: {value: self}

  - id: item_list.favorite_button
    name: お気に入り（行の右端）
    actions:
      - tap:
        summary: アイテムをお気に入りに登録する（アカウントに保存される）
        expect: {selected: self}

  - id: item_list.follow_button
    name: フォローする（下部バー）
    when: フォローしていないとき
    actions:
      - tap:
        summary: フォローする（アカウントのフォロー状態が変わる）
        expect: {hidden: self}

  - id: item_list.register_button
    name: 登録・変更
    actions:
      - tap:
        summary: 登録画面を開く
        expect:
          - when: ログイン中
            screen: register
            via: push
          - when: 未ログイン
            screen: login_alert
            via: modal

  - id: item_list.review_cell
    name: アプリのレビューを書く
    actions:
      - tap:
        summary: ストアのレビュー画面を開く
        expect: {external: app_store}

  - id: item_list.section.recommend
    name: おすすめ（セクションの見出し）
    # actions なし＝見るだけの要素。UI 確認の対象

  - id: item_list.empty_view
    name: 該当なしの表示
    when: 0件のとき

  - id: tab_bar.home
    name: ホーム（タブバー）
    actions:
      - tap:
        summary: ホームタブに切り替える
        expect: {screen: home, via: tab}

  - id: item_list.close_button
    name: 閉じる
    actions:
      - tap:
        summary: 閉じる
        expect: {screen: back, via: dismiss}

  - id: Clear text         # IDが無くラベルしかない要素
    name: 検索欄のクリアボタン（OS）
    by: label
    actions:
      - tap:
        summary: 入力を消し、絞り込みを解除する
        expect: {value: item_list.search_field}

# 要素に紐づかない操作（ページ送りなど）
gestures:
  - scroll: down
    summary: 末尾に近づくと次のページを取得して一覧に足す
    expect: {value: item_list.count_label}

# この画面に着いたときに、自動で出ることがある画面
auto_shows:
  - release_notes                                   # 入ったときに出ることがある
  - {screen: review_dialog, after: image_viewer}    # 画像ビューアから戻ったときに出ることがある
```

- **`names` は呼び名、`summary` はできること。** 軸が違うので混ぜない。「記録画面で〜したい」のように**通称で指されたとき**に引くのが `names`（社内の呼び方、日本語表示名）。「お気に入りに関わる画面はどこか」のように**機能で探すとき**に引くのが `summary`。`names` に「お気に入りを登録できる」を書くと別名リストとして濁り、`summary` に通称だけ書くと機能で引けない
- **`summary` は全画面ぶん読んで候補を絞るためのもの。** だから1行に収める。絞ってから候補の `elements` を読む2段にすると、全画面の `elements` を読むより安い
- **画面idはファイル名。** `id` フィールドは持たない。`screens/item_list.yaml` の id は `item_list` で、`expect` の `screen` はこのファイル名を指す。中にも id を書くと不一致が起きたときに「ファイルは存在するのにどこからも指されていない」状態になり、どちらが正かが読む側の実装次第になる
- **`files` は画面とファイルの対応を書き留めるもの**（VC / VM / View）。型名が揃っているコードベースなら grep で導出できるが、**揃っている保証がない**（セルが `RowCell.swift`、VMが `ItemsPresenter` など）。導出に頼ると少なく返ったことに気づけないので、書いておく
- **網羅ではない。** `diff × files` は対象画面を引く手がかりだが、**載っていないファイルだけを触ったPRは当たらない**。当たらなかったことを「この画面は無関係」と結論しない
- **`files` は鮮度の基準にもなる。** `check` はこのリストと yaml のコミット日時を比べて、マップが実装に追いついているかを出す。載っていないファイルの変更は検出できない
- **`files` は両方向に使う。** `route.py which` は差分のファイル名から対象画面を引く（変更 → 画面）。逆に、機能名で画面を絞ったあとは**読むべきソースの一覧**になる（画面 → ファイル）。**マップはコードを読まずに済ませるためのものではなく、読む範囲を決めるためのもの。** どちらの向きも `files` が薄いと効かない
- **ただしIDを振ったファイルは必ず含める。** セルやサブビューに振ったなら、そのファイルを足す。ID生存チェックのスコープになるので、狭すぎると生きているIDを `dead` と誤判定する（広すぎる側は誤判定しない。鈍るのは「IDが別画面へ引っ越した」の検出だけ）
- **共有コンポーネントは `files` に入れない。** 複数画面で使うボタンやセルを書くと、それを触ったPRで全画面がヒットして対象が絞れなくなる。その画面専用のファイルだけにする

## 階層ごとの説明（`summary`）

AI が「〜したい」から目的の画面と操作を探すときのキーになる。**どの階層でも、人が読む1行の説明は `summary`** にそろえる。

| 階層 | `summary` に書くこと | ほかの説明の欄 |
|---|---|---|
| 画面 | 何の画面で何ができるか | `names`: 画面の呼び名 |
| 要素 | （任意）何のための要素か | `name`: 画面での見え方。場所も添える。パターンの要素は ID に何が入るかも書く |
| アクション | その操作で何をするか。「〜する」「〜を開く」の形 | `note`: 条件や注意 |

- **アクションの `summary` は、画面の文言を写さず何が起きるかを書く。** 表示が「フォロー中」でも、押して出るのが解除と共有のメニューなら「フォロー解除・共有のメニューを出す」と書く。表示と結果がずれる要素ほど効く
- **状態を変える操作（フォロー、登録、削除、設定の切り替えなど）は、`summary` に何が変わるかが分かるように書く。** テストケースを立てる側は、`summary` から押してよいかを判断する
- **`summary` はフローのコメントになる。** 組んだフローはそのままレビューに出るので、「何が起きるか」を書けていないと、人が導線を確かめられない

## elements

**1エントリ = 画面の1つの要素。** 「何か・いつ出るか・押すとどうなるか」を1か所に置く。同じ要素への操作（`tap` と `text` など）は、同じ要素の `actions` に並べる。

| | 意味 |
|---|---|
| `id` | 要素の accessibilityIdentifier。**補間で組まれるIDは末尾に `*` を付けてパターンで書く**（`item_list.cell.*`）。同じ種類の要素が複数並ぶことを表し、どれを押すかはスクリプトが実行時に決める |
| `name` | 画面での見え方。**場所も添える**（「メニューボタン（左上）」）。パターンの要素は ID に何が入るかも書く（「ID は表示中の名前」） |
| `summary` | （任意）何のための要素か |
| `when` | その要素が出る条件。人が読む文（下の「when」） |
| `by: label` | **IDが無く、ラベルでしか指せない要素のとき。** `id` をラベル文字列として扱う（`tapOn: { text: }`）。ローカライズで壊れるので、自分で振れるならIDを振る。OS提供の要素（検索キーのクリアボタン等）とシートの選択肢だけの逃げ道。パターンにはできない |
| `in_tree: false` | ビュー階層に行が出ない要素。座標が要る ⇒ **ここでフローが切れる** |
| `actions` | その要素への操作。**無ければ見るだけの要素**（UI 確認の対象、読み込み完了の目印、`expect` の観測点） |

- **見るだけの要素も書く。** 「このセクションを見たい」という確認項目は、plan の `see:<id>` で指す（スクリプトが見えるまでスクロールして確かめ、撮る）。`expect` や `ready` が指す ID も、どこかの画面の要素として定義されている必要がある（`check` が確かめる）
- **行の中の要素（`item_list.cell.title`）は、行とは別の要素として書く。** 行のパターン（`item_list.cell.*`）の前方一致にも当たるので、書いていないと、スクリプトが「見えている1件目の行」としてタイトルを選ぶ
- **一覧の行はパターンで書く。何番目かを ID に焼き込まない。** どの行を押すかはテストのときの選び方で、画面の事実ではない。条件が無ければスクリプトが**画面に見えている1件目**を押し、条件があれば plan の `pick` に書く（sim-test-report の test-case-builder）。特定の1つを名指しする必要があるのはテストケースの側で、`tap:item_list.cell.牛乳` のように ID まで書けば当たる
- **画面外の要素でも書いてよい。** 押す前・見る前に、スクリプトが必ず見えるまでスクロールする（`scrollUntilVisible`）。マップにスクロールの操作を書かない
- **`by: label` を使う前に、その要素にIDを振れないか確かめる。** 同じファイルの `Text` や `Button` なら `.accessibilityIdentifier()` を足すだけで済む。**逃げ先が表示名だと、ローカライズを差し替えるPRで死ぬ** — セレクタに文言を使わない理由そのもの。表示名と別に不変な識別子が必要なら、`enum` に `identifier` を足すなどして作る
- **`by: label` を使った箇所は、IDを振れない理由を手順6で報告する。** 振れるのに使っていないかを人が確かめられるようにする
- **タブバーの項目は、それが出ている画面ごとに書く。** 各画面から「タブを切り替える」操作ができるという事実なので、その画面の要素として並べる

## actions

**1エントリ = 1つの操作。** キーが操作の種類で、`tap` / `text` のどれか1つを値なしで持つ（`- tap:`）。対象は要素の `id`。

| | 意味 |
|---|---|
| `tap` | タップする。フローの `tapOn` になる |
| `text` | **文字を打つ操作。** 打つ文字はマップに書かない（テストケース側が決める）。フローでは前の文字を消してから打つ。ピッカーやスライダーのような値の指定はこれではない |
| `summary` | その操作で何をするか（上の「階層ごとの説明」） |
| `note` | 条件や注意。人が読む |
| `expect` | **機械が確かめる結果。** 下の表のどれか。1つなら `{...}`、複数ならリスト |

- **入力と送信は別のエントリにする。** デバウンス（入力が止まってから送る）と送信キーを叩くのは結果が違う操作で、片方だけ壊れることがある。入力は入力欄の `text`、送信キーは `Search` 要素の `tap` のように分けて書く
- **ピッカー（ドラムロール）・スライダー・日付選択は、いまのスキーマでは書けない。** IDで叩ける操作ではなく、ホイールのスワイプや目標値へのドラッグになるため、**そこでフローが切れる**。載せずに手順6で「載せられなかった操作」として報告する。キーを増やすのは、実際にそれを含む画面をマップするときに形を決める（Maestroに直接動かすコマンドが無く、いま決めると外す）

## expect

**遷移も結果の1つ。** 「移った先の anchor が見える」という結果として、ほかの結果と同じ欄に書く。

| 種類 | 意味 | スクリプトが確かめること |
|---|---|---|
| `screen` + `via` | 別の画面に移る。`via` は `push` / `modal` / `tab` / `back` / `dismiss` | 移った先の anchor（と `ready`） |
| `visible` / `hidden` | 要素が出る / 消える | その要素が見える / 見えない |
| `selected` / `value` | 要素の状態 / 値が変わる | 選択状態、（値は要素が見えることまで。値そのものは証跡で見る） |
| `external` | アプリの外に出る（Safari、App Store、電話）。値は行き先の名前 | 確かめない。アプリに戻す |

- **`self` はその要素自身を指す。** パターンの要素なら、実際に押した1つ
- **1つのアクションに複数の `expect` を書いてよい**（リストにする）。全部確かめる
- **状態で結果が分かれるときは、`expect` を `when` つきのリストにする。** 全部の項目に `when` を書く（混ぜると `check` が止める）。どの枝を使うかは、確認項目の前提（plan の `when`）で決まる
- **各画面は「そこから行ける先」だけを書く。** 逆方向（この画面への入り口）は書かない。全画面の `expect` を読んで使う側が逆算する。こうしておくと、遷移を変えたPRではその画面のファイルだけ直せば済む
- **戻る操作は `screen: back`。** `via` は `back` か `dismiss`。**戻り先は書かない** — 同じ画面に複数の入口があれば、戻り先は来た道で変わる（一覧から入れば一覧、お気に入りから入ればお気に入りの手前）。1つに決めて書くと、ほかの道では嘘になり、読む人もその値を信じる。スクリプトが歩いた履歴から出す
- **`via: tab` はタブの切り替え。** 経路を選ぶとき、同じ長さならタブバーを通る方を採る（画面の下の方のカードを押すより確実）。push と区別して書く
- **`expect` は「その操作で変わるもの」を指す。** 操作しても変わらない要素を指すと、**操作が効かなくても通る**。一覧の絞り込みで `一覧の行` を指すのが典型で、行は元からあるので何も確かめていない。`summary` に書いた変化と `expect` が対応しているか読み返す
- **要素の状態も観測点になる。** 選択・非活性・チェックはビュー階層に出るので（ダンプの状態の欄に `選択`）、セグメントやタブの切替は**その要素が選択状態になったこと**（`selected: self`）で確かめられる。押すと消える要素は `hidden: self` で確かめる（観測点を別に置かなくてよい）
- **1つの操作の結果を「確かめられる／られない」で割る。** 全か無かにしない。絞り込みなら「入力が入った」は入力欄の値で確かめられるが、「一覧が絞られた」は件数も空表示も無ければ確かめられない。**確かめられる方を `expect` に置き、確かめられない部分を手順6で報告する。** まとめて「置けない」と結論すると、置ける観測点まで落ちる
- **全エントリが同じ `expect` になっていたら間違っている。** 操作ごとに結果が違うのだから、観測点も違うはず。指せる要素が無いなら、それは**確かめられない操作**なので `expect` を書かずに手順6で報告する
- **アクションシート・アラートは画面として扱う。** 操作できるものの集合が変わる状態なので、開く操作から `expect: {screen: <シート>, via: modal}` を張り、選択肢はそのシートの画面の要素に書く。閉じる選択肢は `screen: back, via: dismiss`。別ファイルにすれば `anchor` / `elements` / 経路計算がそのまま使える
- **シートの選択肢はIDで指せないことが多い。** `UIAlertAction` は `accessibilityIdentifier` を素直に持てず、SwiftUIの `.confirmationDialog` 内の Button もIDが提示後のシートに伝わるか分からない。**手順5で実測し、IDで叩けるならIDを、駄目なら `by: label` を使う**

## when

**出る条件、結果が分かれる条件を、人が読む文で書く。** 要素の `when` は「その要素が出る条件」、`expect` の `when` は「その結果になる条件」。

```yaml
- id: item_list.follow_button
  when: フォローしていないとき          # 出る条件
- id: item_list.register_button
  actions:
    - tap:
      expect:
        - when: ログイン中               # 結果が分かれる条件
          screen: register
          via: push
```

- **スクリプトは意味を読まない。** 確認項目の前提（plan の `when`）に**同じ文言**があるかだけを見る。だから、テストケースを立てる側がマップの文言をそのまま写せるよう、短く言い切る（「ログイン中」「未ログイン」「0件のとき」）
- **条件つきの要素や枝は、前提に同じ文言が無い限り経路に使わない。** 出るかどうか、どちらに着くかが状態で決まるので、前提なしで通ると着く先が読めない。経路の途中でしか通れないなら `route.py` が「条件つき」と言って止まる
- **画面が分かれる状態は、見るだけの要素 + `when` で書く。** 0件のときだけ出る空表示、エラー時の再読み込みボタンなど。到着した時点の状態で、操作の結果ではない。確認項目の候補になる（ただし今のデータで踏めないことが多い）

## ready

**読み込み完了の目印。** anchor は画面が出たら見えるが、中身はまだくるくるのことがある。着いた直後に撮ると、読み込み中の証跡になる。

```yaml
ready:
  any: [item_list.cell.*, item_list.empty_view]   # どれか1つが出たら
  all: [item_detail.title, item_detail.body]       # 全部出たら
```

- スクリプトは、移った先の anchor → `ready` → アニメーションの落ち着き待ち（上限3秒）の順に待ってから、次の操作か撮影に進む
- **データの有無で出るものが変わるなら `any` に両方を並べる。** 行があれば行、無ければ空表示。片方だけだと、もう片方のときに待ちきれず落ちる
- **中身の無い画面（設定の固定リストなど）には書かない。** anchor で十分
- 指す ID は、どこかの画面の要素として定義されている必要がある（`check` が確かめる）

## gestures

**要素に紐づかない操作。** いまは `scroll: down` / `scroll: up` だけ。ページ送りのように、目標を ID で指せない操作を書く。

```yaml
gestures:
  - scroll: down
    summary: 末尾に近づくと次のページを取得して一覧に足す
    expect: {value: item_list.count_label}
```

- **画面外の要素を見る・押すためのスクロールは書かない。** それはスクリプトが要素ごとに入れる。ここに書くのは、スクロールすること自体に結果がある操作だけ
- 回数はデータ次第なので、結果は `expect` で確かめる

## auto_shows

**その画面に着くと、こちらの操作と関係なく自動で出ることがある画面**（レビュー依頼、お知らせ、キャンペーンのダイアログ、コーチマーク）。出るかどうかは起動回数・データ・サーバーの応答で決まる。

**自動表示も画面として書く。** 1つのダイアログに1ファイル。`anchor` をダイアログそのものに振り、閉じる操作を `screen: back, via: dismiss` で書く。命名・IDの振り方・実測・`check` が、ほかの画面と同じルールで効く。

```yaml
# screens/review_dialog.yaml — 自動で出るダイアログ
anchor: review_dialog
names: [レビュー依頼]
summary: 起動3回目以降にランダムで出る
elements:
  - id: review_dialog.later_button
    name: あとで
    actions:
      - tap:
        summary: 閉じる
        expect: {screen: back, via: dismiss}
```

**出る場所の画面の側に書く。**

```yaml
# screens/detail.yaml
auto_shows:
  - release_notes                                        # 入ったときに出ることがある
  - {screen: review_dialog, after: image_viewer}         # 画像ビューアから戻ったときに出ることがある
  - {screen: rate_dialog, after: [image_viewer, video_viewer]}
```

| 項目 | いつ確かめるか |
|---|---|
| 画面 ID だけ | その画面に**入ったとき**（push / modal / tab で着いたとき）。戻る・閉じるで戻ったときは確かめない |
| `after` つき | `after` に書いた画面から**戻ってきたとき**だけ。ビューアを閉じた直後に、開いた元の画面の上に出るダイアログなど。複数の画面から戻ったときに出るなら `after` をリストにする |

**マップが持つのは「出ることがある」という事実だけ。** 邪魔か確かめたいかはテストケースが決める。

| 項目 | フローがすること |
|---|---|
| ふつうの項目 | 着いたら、その画面の anchor を待つ**前に**「自動表示が出ていたら、その閉じる操作を叩く」 |
| `from: review_dialog` の項目（自動表示そのものを確かめる） | 出る画面まで行き（`after` つきなら after の画面へ行って戻り）、閉じずに出るまで待つ（下の画面の anchor は待たない）。以降はほかの画面と同じで、閉じる操作も `do` で確かめられる |

**自動表示が出ている間、下の画面はアクセシビリティのツリーから隠れる**（シートやダイアログがモーダルで前に出るため。AozoraReader で実測）。だから先に閉じてから下の画面の anchor を待つ。戻ったときに出るものを `after` で書いておかないと、フローは戻り先の anchor を待ったまま落ちる。

- **並べるのは、実際に出る画面だけ。** 出ていないときの確認に1つあたり約7秒かかる（Maestro が「無い」と決めるまで待つ）。並べた画面に着くたびに払うので、念のために全画面へ並べない。**`after` で絞れるものは絞る** — 関係ないときに待たない
- **同じダイアログが複数の画面で出るなら、ファイルは1つで、それぞれの画面に並べる**
- **操作で開くシートやアラートとは別物。** そちらはこちらの操作で開くので、開く操作の `expect` に `screen` を書く。自動表示は、こちらが何もしなくても出るので開く操作が無い。`auto_shows` がその代わりになる
- **閉じる操作に ID が振れないとき**（`UIAlertAction` のボタンなど）は、ほかの要素と同じく `by: label`。ただし**ダイアログ自体には anchor の ID が要る**
- **OS のダイアログ（通知やトラッキングの許可）は書けない。** アプリの外のもので anchor を振れない。手順6で報告する

## stub

**まだ書いていない画面。** `expect` の `screen` の先として必要なので置く。最低限 `anchor` と、そこから出る操作（戻る操作など）。他のフィールドは書いても書かなくてよい。`stub: true` の意味は **`elements` が網羅ではない**ということだけで、読む側はこの画面の操作一覧として扱わない。次にこの画面を書くときの対象リストにもなる。

```yaml
# screens/settings.yaml
anchor: settings
stub: true
elements:
  - id: settings.item_list_cell
    name: アイテム一覧（行）
    actions:
      - tap:
        summary: アイテム一覧を開く
        expect: {screen: item_list, via: push}
```

## 古い形からの移行

`actions` / `states` を画面に持つ古い形のマップは、`route.py` が読まずに止まる。変換スクリプトで移す。

```bash
python3 ~/.claude/skills/screen-map/scripts/migrate_map.py --repo <アプリのリポジトリ>          # 変換結果を見る
python3 ~/.claude/skills/screen-map/scripts/migrate_map.py --repo <アプリのリポジトリ> --write  # 書き換える
```

- `tap` / `text` を ID ごとにまとめて `elements` にする。`to` + `kind` は `expect: {screen, via}`、`kind: back` / `dismiss` は `screen: back`
- `result` はアクションの `summary` に、`expect: <ID>` は `expect: {visible: <ID>}` に
- `states` と `scroll: <ID>` と、`expect` が指していた観測点は見るだけの要素に。`scroll: down` は `gestures` に
- `select`（`index` / `capture`）は捨てる。どれを押すかはスクリプトが実行時に決める
- **機械に決められないものは一覧で出る**（`result` に書いてある条件、要素の `name`、遷移の `summary`）。直してから `route.py check` を通す。yaml のコメントは消えるので、git の差分で確かめる
